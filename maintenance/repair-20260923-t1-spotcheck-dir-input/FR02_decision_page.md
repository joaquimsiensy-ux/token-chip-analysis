# FR-02 裁决页（大白话）：目录输入案的"事后覆盖"防线要不要补

> 来源：codex 收官 review r1（`final_review_T1_reply_r1.md` FR-02，P1）。本页只摆事实与选项，由用户拍板；T2（FR-01/FR-03）不等本裁决。

## 1. 背景（发生了什么）

9.0.3 之后，时间抽查可以直接吃 `data/v2` 目录。为了不在发布期重算整个目录的哈希（§1.2 边界），时间收据绑的是一份"已签名的输入清单"（`anchor_plan.input.json`，里面记着每个叶子文件的路径/大小/哈希），而不是叶子本身。

codex 做了个实验：目录案全部通过后，把 `data/v2/run_1/logs.parquet` 整个覆写成另一份合法 parquet，清单、计划、收据都不动。结果：
- 重新跑时间抽查的语义重放 → 立刻报 `input sha256 mismatch`（生产期防线有效）。
- 但不重跑，直接走 −1 交接 READY、verify、发布闸 → 全部 exit 0（消费期没人去看叶子）。
- 对比文件输入案：merged 文件被同长度改动 → 立刻被拒。所以目录输入比文件输入弱一档。

## 2. 真实流程里现有的防线（我亲核过）

- 案内脚本 `build_data_map.py`（模板复制到每个案）会把案根下**所有**叶子（含 `data/v2/run_*/logs.parquet`）登记进 `data_map.json`，交接 verify 会核这些叶子的大小/哈希。OPN 案 172 件里就有 v2 叶子。codex 的正控制实验也证实：叶子登记后再覆写，verify 立刻报"哈希/大小漂移"。
- 所以**只要 data_map 登记齐全，覆写会被 verify 抓住**。漏洞在于：skill 没有强制"时间抽查用的目录叶子必须出现在 data_map 里"——这个脚本是案内模板，改一下、漏一下，防线就没了，而且没人会报警。

## 3. 后果（不补会怎样）

- 只影响**目录输入案**（QUQ 是第一例；OPN/BITCOIN 是文件输入不受影响）。
- 风险场景是"自己人"误操作：重采集、覆盖缓存后忘了重跑时间抽查，旧的 PASS 继续有效，报告的对账证据与原始数据脱节。不是外部攻击面。
- 现状可撤销：什么都不做也不会破坏已有案。

## 4. 选项

| 选项 | 做什么 | 代价 | 效果 |
|---|---|---|---|
| A 不补（接受风险） | 只在 references 里写一句"目录案重采集后必须重跑时间抽查" | 0 代码；文档 +1 行 | 靠人记住，和现在一样 |
| **B 补一道必经关联（推荐）** | 另开工单 T3：EVM 交接 READY 生成时，若时间收据的输入是目录，强制清单里每个叶子都在 `data_map.files` 登记且路径/大小/哈希与清单一致，否则拒 READY；verify 沿用现有叶子核验 | 改 `handoff_manifest.py` 一处＋测试；不重算目录哈希（叶子哈希 data_map 已算过一次）；上下文增量小 | 覆写叶子后 verify 必拒；清单与 data_map 脱节也拒 |
| C 重议 §1.2 边界 | 消费期直接展开清单，逐叶子重算大小/哈希 | 每次 verify/发布闸都要哈希全部 v2 叶子（QUQ 级别 v2 目录以 GB 计，每次几分钟起） | 最强，但重复劳动、发布慢 |

## 4.1 codex 收官 review r2 的技术意见（0923 补，原文见 final_review_T2_reply_r2.md §c）

- 9.0.4 之后重做覆写实验：现状与修复前一致，没有变差；正控制（叶子登记进 data_map 后覆写）verify 立刻报"哈希/大小漂移"。
- **B 按上面原文写法不够完整**：READY 生成时只比"清单 vs data_map 声明"证明不了当前实物一致，verify 还要独立核覆盖关系，直接发布入口（audit_release_gate）也要接；另外交接校验对超过 64 MiB 的大文件用的是"头尾分片哈希"，codex 实测同大小改中间字节能躲过这个指纹——所以 B 要做成"增强版"：覆盖生成/校验/发布三个入口＋对时间目录叶子用完整哈希＋检查文件集合变化，估计动 2–3 个生产文件加测试。
- **C（消费期重新枚举并完整哈希目录）是代码改动最小的完整闭环**，可直接复用现有目录身份计算函数；代价是每次 verify/发布都要完整读一遍 v2 目录（QUQ 级别以 GB 计）。
- A 不提供机器防线。

## 5. 推荐与理由（按 codex 意见修订）

我原推荐 B，codex 指出原文 B 有两个漏洞（64 MiB 以上大文件的头尾分片指纹、发布入口未覆盖），修好就成了"增强版 B"，改动面不比 C 小。修订后的推荐：**C，但只对目录输入案触发**（时间收据 kind=directory 时，READY/verify/发布闸重算目录完整身份并与签名清单比对）。理由：一次改动、完整闭环、复用现有函数；代价是目录案每次 verify 多读一遍 v2（分钟级），目录案目前只有 QUQ 一例，可接受。若你更在意 verify 速度，选增强版 B。不建议 A。

## 6. 需要你拍板的一句话

选 A / 增强版 B / C（限目录案）。选定后我按 T2 同样流程（工单→codex 复核→施工→盲审→收官 review）另开 T3，版本走 9.0.5 或并入 9.0.4 由复核定。
