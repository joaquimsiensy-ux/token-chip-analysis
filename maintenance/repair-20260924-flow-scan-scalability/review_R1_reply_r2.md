**③ `preserve_insertion_order`：切换方案可行，但现有解释没有得到实验支持。**

先纠正锚点：**W L46 的 `:193` 应为 `:194`**；生产 L193 设置的是 `memory_limit`。

内存实验使用唯一数值键，执行：

```sql
SET preserve_insertion_order=false;
CREATE TEMP TABLE x AS
SELECT (i * 7919) % 3000000 AS c
FROM range(3000000) r(i)
ORDER BY c;
```

通过 `ORDER BY rowid` 检查写入次序，而非依赖无序 SELECT 的返回顺序：

| 数据量 / threads | CTAS 时 false：下降次数 | CTAS 时 true、随后恢复 false：下降次数 |
|---|---:|---:|
| 1,000,000 / 4 | 0 | 0 |
| 3,000,000 / 8 | 0 | 0 |

这证明：**本机 1.5.4 的这些实验中，false 并未破坏显式 CTAS `ORDER BY` 的写入顺序；临时 true/false 切换也有效。**不能由此承诺所有规模和执行计划，但同样不能把“false 导致 CTAS 不保序”当作本次已核实事实。

建议将 W L46 从“**边表按候选列物理组织**”至“逐候选查询保留 `ORDER BY ts`。”替换为：

> **边表按候选列物理组织**：sink_edges 使用显式 CTAS ORDER BY t, ts，spray_edges 使用显式 CTAS ORDER BY f, ts。基线 `:194` 设置 preserve_insertion_order=false；DuckDB 1.5.4 本机内存实验中，显式 CTAS ORDER BY 在该设置下仍按排序结果写入，不据此宣称任意规模均已验证。若保留 CTAS 前临时设 true 的实现，须用 try/finally 恢复 false。微夹具按 rowid 核验写入顺序，规模夹具结合查询计划、可取得的扫描统计和逐候选耗时核验过滤效果；仅耗时下降不能证明物化表避免了全扫。逐候选查询继续保留 ORDER BY ts。
