机制核验：每个 CTAS 的 EXPLAIN JSON 均验证源扫描数；EVM 每份 eflow 展开仅 1 logs reader + 1 blocks reader（两个 READ_PARQUET 节点是一次边源扫描的两个输入，不是两次 eflow）。DuckDB 微夹具每个 CTAS 只有 1 src.edges scan。
sink_net 计划为 CROSS_PRODUCT 两行 sides + HASH_JOIN SEMI（CASE WHEN k=0 THEN t ELSE f END=#0）+ HASH_GROUP_BY；没有 DELIM_JOIN 或逐候选 OR/非等值连接。
四处原逐候选操作：sink rows→sink_edges WHERE t=? ORDER BY ts；net→net_map.get(t,0) 无 SQL；spray rows→spray_edges WHERE f=? ORDER BY ts；top→spray_edges WHERE f=? GROUP BY t ORDER BY v DESC LIMIT 500。新候选查询计划只含物化表，无 READ_PARQUET、edges、eflow。
保序：诊断在两个 CTAS 执行后直接读取 current_setting 确认 true，按 rowid 的 (候选列,ts) 相邻下降数均 0；生产 helper 的 finally 恢复 false。sink_edges/sink_net 在建 spray_edges 前 DROP。
过滤效果边界：计划含候选地址过滤，输出 cardinality 显著少于物化表行数，但采到的 operator_rows_scanned 等于物化表总行数；这些统计不能证明跳过 row groups。结论仅为消除逐候选底层 parquet 重扫；不宣称所有物化点查避免全表扫描。
逐候选均耗时来自独立诊断执行的 SQL execute+fetchall，按 sink/spray/top 三类分别取平均，含结果传入 Python；不含 EXPLAIN、本候选 Python 滑窗/报告组装和基线 net 单独聚合。新 net 字典读取未单独计时。诊断过程中计划/ANALYZE 会影响缓存，不用其重放总时间替代无插桩 CLI 墙钟。
