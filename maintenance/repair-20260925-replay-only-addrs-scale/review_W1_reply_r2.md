**b）哈希分桶亲核**

使用显式类型 `tag VARCHAR、tx VARCHAR、li BIGINT`，复现结果如下：

| 反例或性质 | 纯内存结果 |
|---|---|
| 同键异值 | 基线冲突键1个，桶内冲突键并集1个 |
| 同键不同块、分别标为 run0/run1 | 两行均落第4桶，冲突检出 |
| 同键端点不同、仅一行命中地址 | 全行查重检出；先地址过滤则漏检 |
| 同键异值、两端均不命中地址 | 全行查重检出 |
| 相同 tx/li、不同 tag | 基线和分桶均无同键冲突 |
| 同 tag、同 tx/li，模拟不同来源 | 同桶，冲突检出 |
| 同值重复查询20次 | 哈希始终相同，返回类型 `UBIGINT` |
| 跨桶 `(a,b)` 合并 | HUGEINT、VARINT 均与基线13行 `ab` 逐行相等 |

增量测试包含普通地址自转、同块相反转账净零、mint、向 Z/DEAD 转入、DEAD 转出、Z 自转及完全重复行。合并前确有同一 `(a,b)` 分布于多个桶；合并后，生产 `_peaks_python` 与 HUGEINT 窗口结果一致。

两点口径需要明确：

- 哈希碰撞不会使当前方案漏检：哈希只决定桶，桶内仍按完整 `(tag,tx,li)` 分组。
- 合法通道清单要求 tag 唯一，见 `channels_preflight.py:413-420`。不同通道 tag 不同，本来就是不同去重键；不应把它描述为需要跨通道检出的同键冲突。

**`kept_rows` 等式不普遍成立。**

v2 中 `n_bad_fields` 与 `n_out_of_segment` 可以重叠。构造“正常、段内坏字段、段外正常、段外坏字段、空块号”五行：

```text
n_source_rows = 5
n_bad_fields = 3
n_out_of_segment = 2
相减结果 = 0
VIEW 实际行数 = 1
```

这类 rejected rows 会在 main 提前拒绝，因此不能据此断言正常补算一定出错。但 v1 还有更直接的问题：值为 NULL 时，`NOT okv` 仍是 NULL，既不计 bad，也不进入 VIEW。

```text
输入：正常行1条＋value=NULL行1条
source=2，bad=0，out_of_segment=0，VIEW=1
```

按当前工单，新路径会在桶计数核对时拒绝；基线这组 reject 计数不会触发拒绝。不能把这种改变登记为契约完全不变。

**替换 1.5 的计数来源，并同步替换 2.1(a)/(b)：**

原文：

> `kept_rows = n_source_rows − n_bad_fields − n_out_of_segment`

建议替换为：

> `kept_rows` 为各通道标准逻辑 SELECT 的实际保留行数之和。复用 `build_events` 已有的逐通道 `n = SELECT COUNT(*) FROM ({part})` 查询结果，不新增扫描；仅在 `materialize=False` 时通过内部字段 `acc["_kept_rows"]` 返回，日志、K 计算及桶行数总和断言均使用该值。不得通过修改原有 reject 计数修补此等式；`materialize=True` 路径及所有持久化收据字段保持原样。`main` 向 `followup_peaks` 传入 `kept_rows=rej["_kept_rows"]`。

**c）扫描、投影、资源及精确替代方案**

**当前是每桶三条独立源查询。** 2.1(c) 依次执行冲突检查、桶行数 COUNT、过滤聚合。`raw_rows` 是 VIEW，前一次查询不会替后一次保存结果。

此外，现有 v2 前处理还有 `_v2_probe`、reject 统计、逐通道保留行 COUNT；之后还有 `maxlen`。预检的文件摘要读取亦未包含在“K 次”中。

不能把查询次数直接乘以完整文件大小：不同查询读取的列不同，缓存和执行计划也会影响实际 I/O。

关于列裁剪，本轮用原 `_v2_select` 文本、仅将文件源替换为内存表，检查优化计划：

- 冲突查询保留 logs 的 `block_number/log_index/transaction_hash/topic1/topic2/data`。
- blocks 侧保留 `number/timestamp`。
- 无关 `block_hash/unused_blob` 被裁掉。
- 桶 COUNT 的投影更窄，但仍需读取用于有效性判断的 `data`。
- `hash(...) % K` 没有阻止这些投影裁剪。

**这证明该谓词不妨碍逻辑列裁剪，不是原生 Parquet 解码量实测。** 本轮未取得原生 `PARQUET_SCAN` 文件计划；不能把“只解码所需列”写成已经完成的文件级实证。施工应记录原生计划；桶谓词不能据此宣称能按哈希跳过 Parquet 行组。

**有一个值得采用的精确优化：合并桶计数与冲突检查。**

替换 1.3 为：

> 按 `hash(tag,tx,li) % K = i` 分桶；同一规范化完整键必在同桶。桶内对全部保留行按完整 `(tag,tx,li)` 分组，同时计算行数及 `COUNT(DISTINCT (b,ts,frm,t2,v))`；累计冲突键集合与基线全局检查相等。覆盖跨块及同通道跨 run；不同 tag 按基线视为不同键。禁止仅按哈希判断键相等，禁止在冲突检查前应用地址过滤。命中冲突即按基线措辞退出，不写收据。

将 2.1(c)-3 的“冲突查重＋独立桶行数 COUNT”替换为：

```sql
WITH g AS (
    SELECT tag, tx, li,
           COUNT(*) AS n,
           COUNT(DISTINCT (b, ts, frm, t2, v)) AS variants
    FROM raw_rows
    WHERE hash(tag, tx, li) % {K} = {i}
    GROUP BY tag, tx, li
)
SELECT COALESCE(SUM(n), 0),
       COUNT(*) FILTER (WHERE variants > 1)
FROM g
```

并追加：

> 返回值分别为桶保留行数和冲突键数。冲突为零后才执行现有地址过滤、去重和增量聚合；删除独立的桶行数源查询。冲突取样允许失败路径额外查询。其余日志若增加源查询，必须计入成本。

内存验证：320行返回总计320、冲突0；增加跨块冲突后返回321、冲突1；空桶返回0、0。

**替换 1.6，并同步修改 1.8/docstring、2.3 详细段：**

原文：

> K 桶 ⇒ K 次全量读取（外加 reject 记账与 `maxlen` 各一次流式扫描）。

建议替换为：

> VIEW 不在独立 SQL 之间缓存结果。原伪 SQL 每桶包含三条覆盖源范围的查询；采用2.1(c)合并计数后，正常路径每桶包含两条源查询。另计逐通道保留行 COUNT、reject 统计、v2 值域探测、maxlen、通道预检及失败取样。查询按所需列裁剪，不将查询次数等同于完整文件字节读取倍数。记录实际 SQL、原生 Parquet 扫描投影、执行次数和墙钟；不得登记为“K 次读取”。

**500万行桶的内存量级不能按“500万”直接判断。**

以大部分键唯一、tx长66字符、两个地址各42字符、时间19字符、值最长37字符估算：

- 字符内容约206 B/行。
- 多个字符串描述符、块号和日志索引再占约百余 B/行。
- 仅这些表示就约1.5–1.6 GB。
- 还未计入分组哈希表、DISTINCT 状态、字符串复制、并行缓冲及 blocks 聚合/join。

因此应按**数 GiB 量级**考虑，不能承诺2 GB足够。实际占用取决于唯一键比例、字符串存储和执行器状态；这不是实测峰值。blocks 全局聚合和最终 `ab` 也不受单桶行数直接约束。

哈希均匀只是常见输入下的期望。本轮生成300个不同完整键，专门选择 `hash(...) % 6 = 0`，得到：

```text
K=6，各桶行数=[300,0,0,0,0,0]
SEG_ROWS=50，最大桶超过4×SEG_ROWS
```

**替换开头变更说明中的：**

> 桶大小由哈希均匀性保证……同时消掉……“段规模”阻断

为：

> 哈希分桶消除了由块号集中直接造成的偏斜，但不保证桶行数或内存上限；重复键集中和不均匀哈希分布仍可能形成大桶。资源问题是否解决，以实际桶规模、唯一键数量及默认桶规模的测量为准。

在 1.5/0.8 追加：

> `SEG_ROWS` 是目标平均规模，不是上限；偏斜告警不构成资源验收通过。补充接近默认500万唯一键、宽字符串的单桶资源证据，或将默认桶规模的可行性明确列为未完成项；200万行默认K=1的测试不能替代该证据。

**不建议改成“内容哈希不同才精查”的全局窄表。**

- 两条同键不同内容若 `c=hash(b,ts,frm,t2,v)` 碰撞，`COUNT(DISTINCT c)` 会漏检。
- 随机模型下，一对内容碰撞概率约为 \(2^{-64}\)，但当前要求是精确保留拒绝能力；不能以概率低替代它。
- `h` 碰撞主要增加误报候选，不是上述漏检的原因。
- 要保持精确，可对所有 `COUNT(*)>1` 的 h 组精查原始完整键和内容，**即使 c 相同也不能跳过**。
- 1.097亿行仅 `(h,c)` 两个64位整数即约1.755 GB，尚未计全局分组状态、精查与临时空间；也需修改1.2的全量物化限制。

因此本轮推荐上述局部合并查询，不推荐未经资源验证的全局哈希摘要方案。

**1．0.7-1/2 与2.2统一“是否包含复制行”。**

**2．0.7-3 仍错误限制 provenance 差异。**

原文：

> `replay_stats.json` 除 `producer`……外逐键逐值相等。

`replay_provenance` 还记录 `outputs.balances_final.sha256`。余额输出使用没有 `ORDER BY` 的查询，业务键值相同不保证 JSON 字节顺序相同。

建议替换为：

**3．0.7-6 的表名快照证据不足。**

原文：

> `duckdb_tables()`……不含 `raw_rows/events`……证明未进入全量物化。

它只能证明查询当时不存在这两个名字的表，无法排除其他名字、先创建后删除，或直接对 VIEW 做全局聚合。

建议替换为：

> 在 `materialize=False` 返回后及桶循环关键阶段记录 `duckdb_tables()` 与 `duckdb_views()`；确认 raw_rows 为 VIEW。结合分支源码和实际 SQL/EXPLAIN，证明未执行全量事件表 CTAS，且每次去重 GROUP BY 的输入均受当前桶谓词约束。表名快照和低RSS均不得单独作为证明。

同时给1.2补上必要限定：

> K=1时，允许在已记录的单桶规模内执行该桶 GROUP BY；禁止的是绕过分桶路径对完整事件集另行聚合或物化。

否则默认200万行、K=1与“任何单条全局 GROUP BY 均禁止”存在文字冲突。

**e）常驻测试与 helper**

修正计数后，`followup_bucketed_case` 可构造。280条规范化事件＋20条重复行是合理的小回归，虽非数学上的最小行数，但不必为少几十行增加构造复杂度。

con.execute(

```

```

复制logs不复制blocks；冲突变体也在COPY和元数据签发前注入。bounds必须同步用于done、receipt CLI及channels声明，不能只改一处。

建议2.2追加独立期望值的明确口径：

> Python期望值使用复制前的规范化唯一事件，或先按完整键验证内容一致并去重；先累计每个 `(地址,块)` 的净增量，再按块升序累计余额。t2始终加值，frm仅在非Z时减值；自转保留净零块。初始峰值0、首达块None，仅余额严格大于当前峰值时更新。对地址并集逐项比较，包括Z、DEAD及低于全量门槛的地址。

这与生产块末、严格大于更新、首次达峰口径一致。不能把复制后的原始行直接累计，也不能在块内每笔交易后更新峰值。

`_run(..., *, env=None, timeout=120)`兼容既有调用。但“既有4处调用”不是实际总数：AST查到**13处 `_run` 调用**，均为两个位置参数、无keyword参数；默认行为不变。

**f）回归面与守卫**
