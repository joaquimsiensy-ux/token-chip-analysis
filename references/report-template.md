# 报告结构与写作纪律（庄家行为分析版）

> 框架版本：v2.0（2026-07-14，用户指定九条修改定型；由 v1.1 五问版迭代而来）。
> 本版核心变化：五问改四问（删建仓成本命题、官推改项目方背景调查）；庄级实体改
> P0/P1 标签体系（取代旧"庄#N"扁平计数）；图 1/图 2 前置到 TL;DR 顶部；P0 实体
> 必配全周期流转路径图；正文钱包一律标签制、代币数量一律带【总量X%】；取消行内
> 置信度 tag；观察哨后必须给两档监控建议。

**交付物：自包含单文件 HTML**（图 base64 内嵌），输出到用户工作目录。
管道：先写 `报告.md` + `charts/*.png`（标准图用 `scripts/report/standard_charts.py`，流转图用 `scripts/report/lifecycle_flow.py`），复核修正全部落定后：

```bash
python3 scripts/report/build_html.py --md 报告.md --out 报告.html
```

**监控包按需生成（v3.2，2026-07-18 用户定）**：观察哨清单、两档监控建议、`appendix.json`（含 report-extract 四键）**默认不随报告生成**——用户实测约 3/4 的标的看完报告不买入，监控产物白做。分析报告交付后，**用户确认买入（或点名要监控）时**再按 `monitoring-package.md`「买入后监控包」节补生成并重出带 `--json` 的 HTML（schema 与流程 v3.3 起全在该分册）。观察哨/监控建议/JSON 附录的格式标准**原样有效**，只是执行时机改为按需。

**先审 md 再出 HTML**——复核 agent 和用户都直接读 md，别拿 HTML 当第一稿。PDF 不再默认交付，仅当用户点名要 PDF 时用 `md2pdf.py`（语法兼容）。

## 四问框架（每次分析的固定命题，TL;DR 必须逐问直答）

1. **有几个庄？**（按下节标签体系识别与分级计数：项目方 / 大庄 / 小庄 / 离场庄 / 狙击集团 / 刷量地址）
2. **每个庄什么类型？** ①单地址明牌 ②多地址·互转/gas 同源·明牌 ③伪装分散·行为指纹一致（类型学见 analysis-playbook §6a）
3. **各阵营全历史持仓占比如何演变？**（占**总供应量**的比例；锁仓/销毁必须单列体现；标准图 1/2 呈现，含建仓后加减仓与拉升期是否出货的解读）
4. **项目方背景调查**（创始人与项目历史含黑历史、推特/Discord/Telegram 运营情况、大V关注量、互动数与浏览量、热度综合评估与水军嫌疑；无项目方的看 dev。方法见 research-workflows §1 背景调查路线）

**建仓成本不再是固定命题**（v2.0 删除旧问③）：不再设独立章节；仅当某实体的出货获利、浮盈状态等结论需要成本参照时，按 playbook §6b 方法按需计算并就地引用。

**开放条款——四问之外必答第 5 条"本次特有发现"**：TL;DR 在四问直答后必须带第 5 条——链上任何不属于四问的显著结构性异常（暴跌/暴涨归因、假量对倒矩阵、流动性池异动、治理/权限异动、跨链桥异常等）在此给一句话结论，并单列正文章节展开；确无特有发现时明写"无"（这也是结论，防读者误以为没查）。禁止因"框架未覆盖"而略去。

**问 3 的 vesting 附加要求**：标的带解锁表/vesting 的（阶段 0 已判定），问 3 必须包含"**未来 6–12 个月解锁日程与量级**"小节（数据源见 research-workflows §1 路线 1，多源交叉；与观察哨联动——下一个解锁日就是天然检验点）。纯 meme 币无解锁结构的，此小节免除。

## 标签体系与重要度分级（v2.0 核心，问 1 的呈现标准）

操作定义（认定规则、峰值取法、合并口径细则）见 analysis-playbook §6a；本节管报告怎么写。

| 标签 | 重要度 | 认定标准（实体合并口径=含全部疑似关联地址，同一时刻合并计算） |
|---|---|---|
| **项目方** | **P0** | 金库、创始人、团队、基金会、vesting 托管、项目方做市仓等一切与项目方相关的实体，**无论持有份额** |
| **大庄** | **P0** | **当前**持仓 ≥20% 总供应 或 ≥20% 流通 |
| **小庄** | P1 | **当前**持仓 ≥5% 总供应 或 ≥10% 流通（未达大庄线） |
| **离场庄** | P1 | **同一时刻历史峰值** ≥10% 总供应 或 ≥15% 流通，且当前既非大庄也非小庄 |
| **狙击集团** | P0 或 P1 | 发射/开盘窗口协同狙击的实体，只要识别出就单独打标签、**不与"庄"混排**；当前持仓 ≥20% 总供应或 ≥20% 流通为 P0，否则 P1（历史峰值曾达标但已大幅出货的按 P1，其出货路径仍需完整分析并在正文注明峰值规模） |
| **刷量地址** | P1 | 对倒刷量执行地址（集群），单独打标签；可证明与其他集团关联时标复合标签"大庄#N·刷量地址""离场庄#N·刷量地址" |

- **报告只对以上标签实体展开分析**。其他大户（当前 ≥1% 总供应或 ≥2% 流通、未入任何标签）与散户只作为阵营出现在标准图 1 中，正文不单独分析、不逐个溯源。
- 编号规则：大庄/小庄按当前持仓降序编号（大庄#1、小庄#1…），离场庄按历史峰值降序，狙击集团仅一个时不编号、多个时 #1/#2；项目方不编号（内部钱包编号区分）。
- **钱包标签制（正文与图例的唯一写法）**：`项目方钱包#1`、`大庄#1钱包#2`、`小庄#2钱包#1`、`狙击集团钱包#3`、`离场庄#1钱包#1`。**报告正文（含表格、图、题注）一律用标签，不出现任何形式的地址（截断的也不行）**；标签 ↔ 完整地址对照只放附录 B 与 JSON 附录。类型三分类（问 2）作为实体属性写在小节标题与 JSON，如"大庄#1（类型②·多地址互转）"。

## 二、供给基线与阵营划分
  总供应多口径表（链上实查/第三方流通/名义解锁，见 playbook §1）
  阵营划分表：项目方 / 大庄 / 小庄 / 离场庄 / 狙击集团 / 刷量地址(有仓才列) /
  流动性池 / 其他大户 / 散户 / 锁仓·销毁(如有)——每个阵营的定义、地址数、
  现仓占比（枚数一律带【总量X%】）
  对账关卡结果一句话（三查过关声明）

**★三账本分离与主控盘口径（2026-07-24 GPT5.6 外部复核采纳，实体持仓类结论的口径宪法）**：凡实体在 LP/托管设施有权益的标的，必须并行维护三张互不冒充的账——
  ①**实体成员表**：哪些 EOA/已证专属合约同控（公共池、路由、CEX 热钱包永不入成员，见 methods pool-probe 硬闸）；
  ②**链上位置账**：币停在钱包/池/CEX/销毁地址（按位置如实单列）；
  ③**经济控制账**：谁握有可证明的最终赎回权/受益权——**"庄控制多少"的主答案必须用这张账**＝钱包自持＋可证 LP 赎回权穿透（V3 按 LP NFT 持有人份额、V4 按 poolId+position+owner 逐头寸重放，见 channels V4 条目），未决权益不猜、单列。
  两个反向病例同一制度治：拿位置账当主答案=把庄放进自有池的币写成"已失去控制"（Codex QUQ 报告 26.73% 错法）；拿设施总余额直接归庄=把公用金库当实体仓（Fable QUQ 报告 V4 单例错法）。产物【候选】：完整版交付 economic_control_ledger（每项 LP 权益带所有权证据、目标块可赎回量、防双计 key），/token-update 续跑时以它为控制口径基线。

**触发**：每个 P0 级实体（项目方、每个大庄、P0 级狙击集团）各配一张，放在第三章对应实体小节内。P1 实体不强制，其流转结构复杂且承载关键结论时也可配。

**图的存在目的（v3.8 用户验收硬性，2026-07-20 定）：不看正文、只看这一张图，能把该实体的全部操作一眼看完——包括各地址群之间怎么关联、怎么分仓、怎么归集合并。** 交付前用这个标准自问，过不了就返工（SIREN 实测：初版图缺平行网四仓与卡片占比，用户对照正文仍"一头雾水"，返工 4 版才达标）。

**内容要求**：
- 覆盖该实体全生命周期：币从哪来（铸造/金库/市场买入/接收分配）→ 中转/拆分结构 → 去向终点（CEX / 休眠仓 / 销毁 / 续持 / 在途）；**体系全部构成入图，禁止"图中未单列"式 footnote 带过**
- **每张卡片标注该节点持币量【总量X%】**（缺占比的实测后果：读者拼不出"峰值 68.7%"由哪些卡片构成）
- **分/合动作写在边标签上**：几址→几址、方式（等额原路返还/碎单/一笔清仓）、时点——"怎么分仓、怎么合并"必须图上可读
- **实体归属证据有落点**：把地址群焊成同一实体的证据（gas 同源 N/M、同日形成、等额指纹、出货合流）写在对应边标签或 footnote 锁扣行
- **footnote 还可承载复核后的行为链定性**：对抗复核落定的实体行为定性（如"占位买→关联方吸筹→砸回制造清仓表象→经关联方出货"式一句话行为还原）写进该实体流转图 footnote——读者只看图即得复核后的最终定性，不必回正文找修正，自解释验收实测有效（来源：USELESS(Solana) 分析，2026-07-21）
- 节点命名一律钱包标签制（不出现地址）；关键转移标注时点 + 数量【总量X%】
- 底部账目行必须配平并做**加法自检：期初−期末＝各去向之和**（各项带【总量X%】；SIREN 净出漏算四仓 15.2pp 即因此项缺位、被用户一个加法抓出）；意图不可区分时在账目行并列写（"高位变现 或 做市备货，链上不可区分"）

**工具**：`scripts/report/lifecycle_flow.py` 的 `draw_lifecycle_flow()`——数据驱动自动布局（框高自适应/箭头标签白底垫片/账目行独立灰条），不要再用 chart_style.flow_box 手摆坐标。样图（通用化、数字虚构）：`references/examples/lifecycle-flow-sample.png`。

**防拥挤排版纪律（画前自查，超限就精简或拆图）**：节点标题 ≤14 全角字符；框内每行 ≤16 字符；边 label ≤2 行、每行 ≤14 字符；每列节点 ≤5 个、列数 ≤5；更复杂的结构拆成"主路径图 + 细节图"两张。

## 术语与角色可读性（v3.8 用户验收硬性，2026-07-20 定）

**验收标准：读者（非币圈、非程序员）从头读完报告，不需要向分析者提问就能理解全部关键结论。** SIREN 实测反例：用户读完初版报告后为读懂它连问约 10 个术语/机制问题（原子转发合约/V4/进出轧平/执行器/结算桥/收币台/BFS/可达域/平行静置仓网/尾币）——用户原话"如果每个报告我都要拿来问你 7-10 个问题才能理解的话，就说明报告不合格了"。

三类词分开治理，**首次出现处就地解决**（读者卡壳点在"读到那里不懂"，不能指望翻附录）：

1. **行业专有名词**（V4、执行器、聚合器、结算桥、BFS…）：首现处带一句大白话比喻。SIREN 问答实测有效的比喻直接复用：
   - V4 单例架构＝大商场中央金库（所有店铺共用一个金库，看流水必须穿透到具体店铺）
   - 执行器＝收银台/自动传送带（只负责过手，不是货主）；聚合器＝帮买家比价的中介
   - CEX 结算桥＝交易所的运钞车（全体用户充提共用的公共通道）
   - BFS N 层扩散＝顺藤摸瓜往下最多查 N 步；可达域＝这样能摸到的全部钱包范围
2. **自造角色绰号**（收币台、尾币仓、影子中转、静置仓、原子转发合约…）：起名时优先选自解释的名字；首现处交代三件事——**这是我们起的绰号＋指什么＋为什么这么叫（行为特征）**。例："收币台（我们给某枢纽地址起的绰号：行为像收购柜台——从全网碎单收币、流出只进自家人口袋）"。
3. **机制描述短语**（逐日进出轧平、wei 级等额、广口进单口出…）：正文写成现象白话（"每天进多少出多少、日终余额清零"），机制名保留在括号里供回查。

**角色速查卡**：自造绰号 ≥5 个的报告，TL;DR 之后放一张速查表（绰号｜一句话身份｜在故事里干什么），读者中途忘了随时回查——与"正文零地址、一律标签制"配套。

**交付前自检**：过一遍全文列出所有专名/绰号/机制短语，逐个检查首现处是否已解释——每个未解释的词就是读者未来的一个提问。
