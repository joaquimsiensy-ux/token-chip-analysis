# 阶段 6：复盘与迭代机制（操作手册）

本 skill 的核心设计：**每次分析都让 skill 变得更好**。交付报告（HTML）后立即执行本流程，不可省略。

v3.0（2026-07-18 稳定化）新增四件：质量指标、新规则 candidate 分级、整编模式、预测追踪。背景：前 50 版的复盘引擎只有加法（追加写入）没有减法与校准，导致 playbook 追加式膨胀、单案规则事后拟合风险、以及"只测成本不测质量"——轮次降了 75% 有实证，但初稿是否更准无法回答（2026-07-18 稳定化审计 + codex 交叉复核共识）。

## 为什么有这个机制

本 skill 由五次独立分析（OPN/SIREN/HYPE/FIL/IO，2026-07）的经验平权综合而来。用户曾刻意让每次分析从零开始以避免偏见，实验结论是：**工具性知识（数据源/脚本/坑/流程）复用收益巨大且无偏见风险，而对代币的结论复用会污染判断**。本机制只沉淀前者。

## 流程（四步）

### 1. 生成复盘清单（自动）

交付报告后，回顾本次会话，按五类列出候选条目：

| 类别 | 判定标准 | 目标文件 |
|---|---|---|
| 新数据源实测 | 本次用了 references 里没有的端点/CLI/参数，或实测推翻了已记录的结论（限速变了、字段改了、免费层收紧） | `data-pipeline-<chain>.md` 对应小节 |
| 新坑与对策 | 本次踩了 references 未记录的坑（含环境坑 → `environment.md`） | 对应 pipeline 或 `environment.md` |
| 方法修正 | 分析方法学的改进/反例（如某聚类规则在新场景失效）——**按下节 candidate 分级入库** | `analysis-playbook.md` |
| 脚本新增或变更 | scripts/ 里的脚本本次被修改，或新写了可复用脚本 | `scripts/<chain>/` |
| 遗留 TODO | 本次没解决、下次该补的（如某链 pipeline 待验证条目） | `CHANGELOG.md` Known Gaps |

每条注明：内容、证据（本次会话哪一步）、拟写入的目标文件与小节。

**成本指标（3 个，照旧）**：本次轮次数、Bash 调用数、报告交付用时——追加到 CHANGELOG 条目，跨版本积累优化曲线。

**质量指标（4 个，v3.0 新增，与成本指标同格式追加）**：
1. 初稿关键结论数（TL;DR 直答 + 各章硬结论计数）；
2. 对抗复核判定分布：CONFIRMED / WEAKENED / REFUTED 各多少；
3. 复核翻出的漏检实体数（初稿没发现、复核补上的 P0/P1 实体或观察组）；
4. 传播级数字错误数（TL;DR/图注里被复核抓出的错误数字）。

为什么必须记：只记成本会把"更快"误当"更好"。"复核每次都有修正"不是复核的胜率，是**初稿缺陷率的反面指标**——这 4 个数是"初稿是否在进步"的唯一证据源，目标是 REFUTED 与重复错误跨版本持续下降（codex 交叉复核 2026-07-18 定调）。

### 1b. 新规则分级：candidate → 正式（v3.0 新增）

- **分析方法类**新规则（playbook 的判定/指纹/口径/呈现类）首次入库一律标 **【候选·单案】**（写在条目行首），来源照注；
- 升正式的两条路径（满足其一）：①第二个**独立案例**复现（不同代币、不同会话）；②有明确**机制解释**——能说清"为什么必然如此"而不依赖单案观察（如数学恒等式、协议机制、API 硬约束）；
- **数据工程类**（端点/限速/字段/环境坑/脚本参数）不受此限——确定性知识直接入正式；
- 候选规则在分析执行时按正式规则对待（宁可多查一路），但报告措辞引用时注明"单案经验"；
- 候选条目的转正/降档在整编时统一处理（见 2b）。

为什么：复核发现自动升级为全局硬规则是**事后拟合**——规则能解释上一案，不代表能预测下一案；跨案复现才是泛化证据。历史上"模式已两见"的标注习惯就是这个思想，v3.0 起制度化。

### 2. 用户确认（AskUserQuestion）

把清单呈给用户，选项：**全部写入 / 逐条挑选 / 本次跳过**。未确认前不动 skill 文件。

### 2b. 整编模式（v3.0 新增：迭代引擎的减法，定期强制）

**触发条件（满足任一即在当次复盘时顺带执行，或单独开整编会话）**：
- skill 次版本号尾数逢 0 或 5（约每 5 次分析一次）；
- `analysis-playbook.md` 超过 60KB；
- `docs lint`（scripts/tests/docs_lint.py）抓出交叉引用漂移 ≥3 处。

**动作（只做减法与归位，不引入新规则）**：
1. 同主题散点条目合并成一条主规则（历史病灶：整数仓指纹、流通分母口径各散落 3 处）；
2. 案例叙事压缩为一行来源引用（详情本就在 CHANGELOG 可考古）；
3. 候选规则清点：两案以上→转正；入库超 8 个次版本仍单案→降档移入 CHANGELOG 存档（正文删除）；
4. 全文档交叉引用校对（跑 docs lint + 人工过一遍 SKILL.md 的引用行）；
5. CHANGELOG 归档滚动：活跃文件只留最近 ~10 版，更早移入 `CHANGELOG-archive.md`。

**纪律**：整编前后 git diff 必须逐条可追溯；合并产生的条目在 CHANGELOG 整编记录里注明"合并自哪几条"；拿不准是否还有效的条目**保留并标疑**，不静默删除。

为什么：迭代引擎只有加法时，40+ 版后文档必然膨胀失序（100KB playbook、SKILL.md 引用滞后、规则互相遮蔽——2026-07-18 稳定化审计的直接教训）。

### 3. 写入（确认后）

- 条目写入对应 references 文件的对应小节，行尾注明来源：`（来源：<代币名>(<链>) 分析，YYYY-MM-DD）`
- 脚本变更同步到 `scripts/<chain>/`，必须 `python3 -m py_compile` 通过
- 新的基础设施地址（CEX/MM/程序ID）→ `address-book.md`，附来源与核验日期
- **写入后跑守护三件套**（v3.0：`scripts/tests/` 下 changelog_lint / docs_lint / labels manifest 校验，详见各脚本头注释）——FAIL 先修再收工
- **git 提交**：本次复盘的全部文件变更一个 commit（skill 目录已是 git 仓库，2026-07-18 起）；commit message 首行 = CHANGELOG 条目标题

### 4. CHANGELOG 追加（版本号见下方约定）

格式见 CHANGELOG.md 头部约定。**写入前必跑 `scripts/tests/changelog_lint.py`**——版本号重复（2.21.0 撞号事故）与顺序交错（2.24/2.25 倒排）都实际发生过，并行会话尤其要防。

## 预测追踪（v3.0 新增：分析质量的外部校准）

复核指标（上面 4 个）测的是"初稿 vs 复核"，仍是内部口径；预测追踪测"报告 vs 后来的现实"，是唯一的外部校准。

- **登记**：交付时 appendix.json 的观察哨/监控建议本身就是可检验预测（哨兵触发条件、解锁抛压、协同验证点）。复盘时不必重复造账本——appendix 即登记处；仅当报告正文有 json 外的硬预测（"X 事件前后必有 Y"类）才补记进目录下 `predictions.md`。
- **回看（挂在 /token-update 的 U3c 观察哨核查）**：每次增量更新核查旧哨时，顺带产出三维评分并写进更新简报：
  1. **事实归因**：旧报告的核心账本抽验结果（U4 已有此路）——对/错/未验；
  2. **行为预测**：观察哨触发情况——兑现/未兑现/窗口未到；
  3. **价格结果**：单独记录，**不得反过来证明链上归因正确**（归因可以对而价格受外部事件驱动，反之亦然）。
- **汇总**：整编时（2b）统计累计兑现率写进 CHANGELOG 整编条目。这是回答"这套分析到底准不准"的唯一长期证据。
- 没有增量更新需求的标的，预测自然沉睡——不强制专门回看会话；投后监控（posthold）已覆盖的标的以其触发记录为准。

## 红线（违反即剔除）

1. **复盘条目出现对标的代币的分析结论**（"XX 币庄家在吸筹"、任何评分/判定/目标价）→ 违反铁律 1，剔除。地址标签是事实可入库；"这个地址在出货"是结论，不可。
2. 弃盘评分、吸筹判定等**框架维度**可以沉淀，但**不得携带任何代币的锚点分数/案例数字**。
3. references 是工具性知识的**唯一权威源**；memory 里只放指针，不双写细节。
4. **否定性通道结论入库前必须核查（v1.3）**：写"XX 不可用/未找到/不存在"之前——①列出实际试过的端点/域名清单；②标注穷尽程度（"未穷尽搜索"还是"官方文档确认不存在"）；③与项目 memory 及既有 pipeline 文档交叉核对有无矛盾。错误的否定结论会被"死亡名单禁止重探"纪律锁死，比错误的肯定结论危害更持久（实例见 data-pipeline-robinhood.md 修正记录：一次会话把另一会话已实测可用的 Blockscout/RPC 写成"未找到"，直接损失了合约验证能力）。所有"不可用"结论必须带实测日期，超过 3 个月允许花 1 分钟小请求重探。
5. **可复用脚本必须收编进 skill（v1.3）**：pipeline 文档引用的采集/溯源脚本一律复制到 `scripts/<chain>/` 并参数化（API key 与标的地址移入工作目录 config.json，铁律 5），禁止只留桌面项目目录路径——项目目录会被清理，skill 会断链。标的专属的分析/报告脚本可留项目目录存档，但 pipeline 文档引用它们时须注明"专属存档，非复用件"。

## 版本号约定（v3.0 起两维）

- **skill 版本**（流程+方法，CHANGELOG 主条目）：主版本=架构级重构（工作流骨架变更）；次版本=每次**分析复盘**迭代 +1；修订号=文档小修/笔误。
- **labels 数据版本**（标签库自己的 v4.x 序列）：标签库扩容/重建/数据刷新**不再占用 skill 次版本号**，在 CHANGELOG 记 `labels vX.Y` 前缀条目（挂在当前 skill 版本下），何时重建见 labels/README。
- 唯一性与顺序由 `scripts/tests/changelog_lint.py` 把关；并行会话写入前先 `git pull` 状态确认 + 跑 lint（撞号与倒排都发生过：两会话同日各写 2.21.0）。
