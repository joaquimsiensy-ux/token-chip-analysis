# 阶段 6：复盘与迭代机制（操作手册）

本 skill 的核心设计：**让分析经验能沉淀回 skill**。**触发方式（v6.4.0 起）：仅在用户明确要求复盘时执行——任何工作流（A6/E6/U6）都不自动进入本流程，分析会话交付报告即收工。** 为什么：批量跑币时结论尚未经用户复核，自动沉淀教训等于把可能错误的经验固化进 skill；正确顺序＝交付 → 用户复核确认结论没问题 → 用户下令复盘（2026-07-31 用户定）。分析会话中发现的候选教训随手记进案目录 `retro_notes.md`（只动案目录，不动 skill 文件），等用户下令复盘的会话按下方流程消费。

> **元规则（v4.1.0 2026-07-30，三案复发实证后立）**：凡"实体身份误判/实体漏检"类教训（把托管/设施当庄家、漏掉历史层等），复盘**必须以代码或门禁 diff 收尾**——改工具数据源、加 gate 校验、进复核 prompt 固化段三选一，**纯文字教训不算闭环**。实证：IQ 案（Upbit 托管判大庄）教训写成 memory"待写入 skill"从未落地、PENGUIN 案（Alpha 库存仓判别法）只写进 easy-workflow 未同步完整版、LPT 案（Bitvavo 质押判巨鲸）只留在结论存档——三条文字教训全部未能阻止 PYTHIA 案第四次同族复发（9Z 判小庄），直到 v4.1.0 把它们变成 label_lookup 并源 + entity_identity_gate + build_html G8 三道机械闸。文字教训生效依赖"正确时点被读到"，长流程中必然衰减；机械闸不做就过不去。判断口诀：**写完教训问一句"下一个会话如果不读这段文字，错误还会发生吗？"——会，就必须上闸。**

v3.0（2026-07-18 稳定化）新增四件：质量指标、新规则 candidate 分级、整编模式、预测追踪。背景：前 50 版的复盘引擎只有加法（追加写入）没有减法与校准，导致 playbook 追加式膨胀、单案规则事后拟合风险、以及"只测成本不测质量"——轮次降了 75% 有实证，但初稿是否更准无法回答（2026-07-18 稳定化审计 + codex 交叉复核共识）。

## 为什么有这个机制

本 skill 由五次独立分析（OPN/SIREN/HYPE/FIL/IO，2026-07）的经验平权综合而来。用户曾刻意让每次分析从零开始以避免偏见，实验结论是：**工具性知识（数据源/脚本/坑/流程）复用收益巨大且无偏见风险，而对代币的结论复用会污染判断**。本机制只沉淀前者。

## 流程（四步）

### 1. 生成复盘清单（自动）

**第一步先跑草稿生成器（3.19）**：`python3 scripts/report/retro_draft.py 案目录 --out retro_draft.md`——读 findings.md 等素材按五类关键词启发式出骨架，每条附 `文件:行号` 出处（GOAT 案实测 71 行 findings → 35 条候选）。定位是省打字：召回优先允许误报，**人工勾选删改后用，不许原样当复盘交差**。然后按五类补全：

| 类别 | 判定标准 | 目标文件 |
|---|---|---|
| 新数据源实测 | 本次用了 references 里没有的端点/CLI/参数，或实测推翻了已记录的结论（限速变了、字段改了、免费层收紧） | `data-pipeline-<chain>.md` 对应小节 |
| 新坑与对策 | 本次踩了 references 未记录的坑（含环境坑 → `environment.md`） | 对应 pipeline 或 `environment.md` |
| 方法修正 | 分析方法学的改进/反例（如某聚类规则在新场景失效）——**按下节 candidate 分级入库，归宿按 2c 分流决策树定** | casebook / playbook（见 2c） |
| 脚本新增或变更 | scripts/ 里的脚本本次被修改，或新写了可复用脚本 | `scripts/<chain>/` |
| 遗留 TODO | 本次没解决、下次该补的（如某链 pipeline 待验证条目） | `CHANGELOG.md` Known Gaps |

每条注明：内容、证据（本次会话哪一步）、拟写入的目标文件与小节。

**成本指标（3 个，照旧）**：本次轮次数、Bash 调用数、报告交付用时——追加到 CHANGELOG 条目，跨版本积累优化曲线。

**质量指标（4 个，v3.0 新增，与成本指标同格式追加）**：
1. 初稿关键结论数（TL;DR 直答 + 各章硬结论计数）；
2. 对抗复核判定分布：CONFIRMED / WEAKENED / REFUTED 各多少；
3. 复核翻出的漏检实体数（初稿没发现、复核补上的达标实体或观察组）；
4. 传播级数字错误数（TL;DR/图注里被复核抓出的错误数字）。

为什么必须记：只记成本会把"更快"误当"更好"。"复核每次都有修正"不是复核的胜率，是**初稿缺陷率的反面指标**——这 4 个数是"初稿是否在进步"的唯一证据源，目标是 REFUTED 与重复错误跨版本持续下降（codex 交叉复核 2026-07-18 定调）。

**复盘完备性两道硬检（2026-07-23 QUQ 元复盘新增）**：
1. **修正对照表逐行核销**：复盘完整性的检验标准不是"写了多少"，而是先把本案全部"初稿→修正"对照表列全（**含交付后/投后阶段的翻案**，不只分析阶段的复核修正），再逐行问"这行的方法进册了吗"。复盘结构性偏科于只沉淀最后一段工作——更早但更大的翻案发生时人还在打仗，没空归档（实证：QUQ 案第一轮复盘只覆盖了当日下午的量能考古与制度侧，昨夜发生的全案最大翻案群〔订单流成色等〕滞留 retro_notes，靠用户贴修正表逐行追问才补全入册）。
2. **candidate 清账扫描**：复盘 commit 之后新产生的 candidate（交付后修正、深夜追问的产物）会滞留案目录 retro_notes——下一次复盘会话开工第一步 `grep -n "candidate" <案目录>/retro_notes.md` 清账，凡标注未入册的按五类归位（实证：QUQ 案 A 方案两条 candidate〔庄组纯 EOA 原则、报警归因分解〕写入 retro_notes 的时间在复盘完成之后 11 分钟，滞留至次日元复盘才入库；同类风险还包括复盘写完后忘 git commit——v3.22.0 变更即隔夜未提交，由次日会话补班车，开工时顺手 `git status` 一并检查）。

### 1b. 新规则分级：candidate → 正式（v3.0 新增）

- **分析方法类**新规则（playbook 的判定/指纹/口径/呈现类）首次入库一律标 **【候选·单案】**（写在条目行首），来源照注；
- 升正式的两条路径（满足其一）：①第二个**独立案例**复现（不同代币、不同会话）；②有明确**机制解释**——能说清"为什么必然如此"而不依赖单案观察（如数学恒等式、协议机制、API 硬约束）；
- **数据工程类**（端点/限速/字段/环境坑/脚本参数）不受此限——确定性知识直接入正式；
- **候选规则的运行权限＝只当"查证提示"（v6.2.0 收紧）**：候选可以提示查哪一路、比什么，**不得作为任何结论/定性的依据**——结论必须由本案链上证据独立支撑；报告措辞引用时注明"单案经验"。为什么收紧：候选=未经检验的单案归纳，按正式规则消费等于让未检验经验直接下结论（2026-07-31 存留审计定）；
- **存留审计（v6.2.0）**：候选条目按三判据审计——①机制解释（能说清"为什么必然如此"）②翻案/用户终裁背书 ③用户追问检验——**全不占的从正文删除移入 `attic.md`**（默认不读、不进分析上下文，等于"没做过"；恢复条件=第二案复现或机制补齐）。占任一判据的保留候选身份继续观察；
- 候选条目的转正/降档在整编时统一处理（见 2b）。

为什么：复核发现自动升级为全局硬规则是**事后拟合**——规则能解释上一案，不代表能预测下一案；跨案复现才是泛化证据。历史上"模式已两见"的标注习惯就是这个思想，v3.0 起制度化。

### 2. 用户确认（AskUserQuestion）

把清单呈给用户，选项：**全部写入 / 逐条挑选 / 本次跳过**。未确认前不动 skill 文件。

### 2b. 整编模式（v3.0 新增：迭代引擎的减法，定期强制）

**触发条件（满足任一即在当次复盘时顺带执行，或单独开整编会话）**：
- skill 次版本号尾数逢 0 或 5（约每 5 次分析一次）；
- **任一 playbook 分册超过 60KB**（v6.4.2 修订：原触发对象 analysis-playbook.md 已拆成 ~7KB 路由页永不触发，触发器改盯各分册；四分册拆分动作已于主题拆分时兑现，当前 playbook-entity-cluster-methods.md ~84KB 已超线待整编）——超线动作=按主题再拆或压缩整编，目标单册 <60KB（只定线不定动作=触发器形同虚设的教训保留）。拆分纪律：先冻结规则清单再逐条迁移核对（拆分最易丢规则），禁止凭印象重写；
- `docs lint`（scripts/tests/docs_lint.py）抓出交叉引用漂移 ≥3 处；
- SKILL.md 超过 10KB（v6 骨架硬指标：路由层膨胀＝规则又开始堆回主文件）；
- casebook 单册超过 25KB 或 25 条（casebook_lint 会 FAIL——先合并同族模式，不拆新册）。

**动作（只做减法与归位，不引入新规则）**：
1. 同主题散点条目合并成一条主规则（历史病灶：整数仓指纹、流通分母口径各散落 3 处）；
2. 案例叙事压缩为一行来源引用（详情本就在 CHANGELOG 可考古）；
2b. **变更叙事清出正文（2026-07-31 用户定）**："取代了什么旧条款/哪版删了什么/原条款是什么"类历史一律进 CHANGELOG，正文只留现行规则＋机制依据（数字门槛为什么是这个值的理由必须保留）；废止条款的存量数据迁移桥唯一归宿＝update-workflow 标准迁移条款，其他文件只留一行指针；行尾来源标注（案名，MM-DD）不属变更叙事，保留；
3. 候选规则清点：两案以上→转正；单案候选按 1b 三判据审计——全不占的移入 `attic.md`（正文删除，不再等 8 个次版本），占判据的保留继续观察（超 8 版仍单案时在整编记录里点名复审）；
4. 全文档交叉引用校对（跑 docs lint + 人工过一遍 SKILL.md 的引用行）；
5. CHANGELOG 归档滚动：活跃文件只留最近 ~10 版，更早移入 `CHANGELOG-archive.md`。

**纪律**：整编前后 git diff 必须逐条可追溯；合并产生的条目在 CHANGELOG 整编记录里注明"合并自哪几条"；拿不准是否还有效的条目**保留并标疑**，不静默删除。

为什么：迭代引擎只有加法时，40+ 版后文档必然膨胀失序（100KB playbook、SKILL.md 引用滞后、规则互相遮蔽——2026-07-18 稳定化审计的直接教训）。

### 2c. 教训分流决策树（v6.0.0 新增：每条教训先定归宿，再动笔）

每条经用户确认的教训，**按顺序过以下分流，落在哪层就写哪层，禁止跳到 SKILL.md**：

1. **能机械化吗？** 满足全部门槛——输入确定、误报率低、跨案复现或机制成立（candidate 纪律同款）、能配离线 fixture、失败时的处置动作明确——→ **gate/守护测试**（代码收尾）。这是元规则（文件头）从"实体身份类"到**一切达标教训**的推广；门槛不满足的不硬上闸（低质量闸=狼来了，比没有更坏）。
2. **是判定类失败模式/指纹吗？**（某类判定曾怎么错、靠什么检验区分）→ **casebook 对应册**（六字段结构见 casebook/README.md）。判例带案例出处合法，但不得当结论先验（铁律 1 边界）。
3. **是通道/环境事实吗？**（端点/限速/字段/本机坑）→ **data-pipeline-\<chain\>.md / environment.md**（数据工程类直接入正式，1b 豁免条款）。
4. **是流程缺口吗？**（某步该做没做、顺序错了）→ **对应 workflow 手册**（analyze/easy/update/collect）**或交付 checklist**（report-template 末节）。
5. **以上皆非且全局横切**（跨所有模式、跨所有链的原则）→ 才允许动 **SKILL.md**，且受铁律 7 条封顶（新进＝旧出或代码化）与 10KB 字节预算双重约束。

配套两条：
- **翻案案例默认登记为 evals 候选题**：凡对抗复核/外部复核产生且经用户终裁的翻案，在 `evals/README.md` 题单追加候选行（正式成题可延后到整编时）——翻案是评测题库的唯一供给源。
- 分流拿不准时：先落 casebook（可逆、可检索），整编时再升级为 gate；**禁止**因拿不准而写进 SKILL.md。

### 3. 写入（确认后）

- 条目写入对应 references 文件的对应小节，行尾注明来源：`（<代币名>(<链>)，YYYY-MM-DD）`
- 脚本变更同步到 `scripts/<chain>/`，必须 `python3 -m py_compile` 通过
- 新的基础设施地址（CEX/MM/程序ID）→ `address-book.md`，附来源与核验日期
- **惯犯库回灌（v6.4.1 起挂此处，原为交付后固定动作）**：`python3 scripts/labels/accumulate_offenders.py --apply`——本案庄家实体回灌惯犯库（appendix.json / analysis-state.json 为扫描源，筛查不买入的案子复盘时同样回灌；含 manifest 自动落印）；`sources/serial_conflicts_*.md` 非空时先按 labels/README 三选一裁决再 apply。挪进复盘的原因：结论未经用户复核就入库，错判地址会污染惯犯层——不复盘不回灌
- **写入后跑守护全家桶**（v3.3：`python3 scripts/tests/run_all.py` 一键=三件套 lint + replay_inc/build_html 离线契约测试；改过账本类脚本必跑）——FAIL 先修再收工
- **git 提交**：本次复盘的全部文件变更一个 commit（skill 目录已是 git 仓库，2026-07-18 起）；commit message 首行 = CHANGELOG 条目标题

### 4. CHANGELOG 追加（版本号见下方约定）

格式见 CHANGELOG.md 头部约定。**写入前必跑 `scripts/tests/changelog_lint.py`**——版本号重复（2.21.0 撞号事故）与顺序交错（2.24/2.25 倒排）都实际发生过，并行会话尤其要防。

## 预测追踪（v3.0 新增：分析质量的外部校准）

复核指标（上面 4 个）测的是"初稿 vs 复核"，仍是内部口径；预测追踪测"报告 vs 后来的现实"，是唯一的外部校准。

- **登记**：带监控包的标的（买入的），appendix.json 的观察哨/监控建议本身就是可检验预测（哨兵触发条件、解锁抛压、协同验证点）——appendix 即登记处，复盘时不必重复造账本。**v3.2 起未买入标的默认无 appendix**：其预测=正文点出的天然检验点，自然沉睡不强制回看；仅当报告正文有硬预测（"X 事件前后必有 Y"类）才补记进目录下 `predictions.md`。
- **回看（挂在 /token-update 的 U3c 观察哨核查）**：每次增量更新核查旧哨时，顺带产出三维评分并写进更新简报：
  1. **事实归因**：旧报告的核心账本抽验结果（U4 已有此路）——对/错/未验；
  2. **行为预测**：观察哨触发情况——兑现/未兑现/窗口未到；
  3. **价格结果**：单独记录，**不得反过来证明链上归因正确**（归因可以对而价格受外部事件驱动，反之亦然）。
- **汇总**：整编时（2b）统计累计兑现率写进 CHANGELOG 整编条目。这是回答"这套分析到底准不准"的唯一长期证据。
- 没有增量更新需求的标的，预测自然沉睡——不强制专门回看会话；投后监控（posthold）已覆盖的标的以其触发记录为准。

## 季度质检节拍（3.19 新增：不进单案主流程的两道体检）

按季度（或攒 8-10 案后）在轻会话单独跑，不占分析会话：

1. **脚本分叉盘点**：`python3 scripts/bench/scan_script_forks.py --workroot <工作根>`——同名私版脚本 AST 指纹分组，报告落工作根 `脚本分叉盘点_<日期>.md`（份数/指纹种数/是否已有通用件仍存私版+收编顺序建议）。首轮基线 2026-07-22：439 份 py/358 组/多份组 32，make_charts.py ×21 份 21 种指纹居首。收编节奏仍守"≥3 次稳定重现才固化"（2026-07-15 用户定），盘点只供发现与排序；指纹不同≠必须合并（案专属参数硬编码属正常），收编指参数化进通用件。
2. **时间封存测试（后见拟合体检）**：选一个已定案 ≥1 个大庄级实体的案子（"无庄散户盘"测不出东西）——`truncate_dataset.py --data-dir 案/data --out-dir <临时目录> --ratio 0.75` 出封存副本（绝不写原始目录）→ 指向副本重跑该案聚类判级出封存版 analysis-state → `holdout_diff.py --holdout 封存版 --full 全量定案版` 对比实体集合/成员/判级差异（exit 1=有差异人工审）。**衍生 json（cex_map/首见表等）必须从副本重生成**，复用全量版衍生件=封存穿帮。检验的问题：只看前 75% 历史时实体判定是否还成立、封存尾段是否延续协同——方法有没有"后见拟合"。差异发现按 candidate 纪律入库。

## 红线（违反即剔除）

1. **复盘条目出现对标的代币的分析结论**（"XX 币庄家在吸筹"、任何评分/判定/目标价）→ 违反铁律 1，剔除。地址标签是事实可入库；"这个地址在出货"是结论，不可。
2. 弃盘评分、吸筹判定等**框架维度**可以沉淀，但**不得携带任何代币的锚点分数/案例数字**。
3. references 是工具性知识的**唯一权威源**；memory 里只放指针，不双写细节。
4. **否定性通道结论入库前必须核查（v1.3）**：写"XX 不可用/未找到/不存在"之前——①列出实际试过的端点/域名清单；②标注穷尽程度（"未穷尽搜索"还是"官方文档确认不存在"）；③与项目 memory 及既有 pipeline 文档交叉核对有无矛盾。错误的否定结论会被"死亡名单禁止重探"纪律锁死，比错误的肯定结论危害更持久（实例见 data-pipeline-robinhood-channels.md 修正记录：一次会话把另一会话已实测可用的 Blockscout/RPC 写成"未找到"，直接损失了合约验证能力）。所有"不可用"结论必须带实测日期，超过 3 个月允许花 1 分钟小请求重探。
5. **可复用脚本必须收编进 skill（v1.3）**：pipeline 文档引用的采集/溯源脚本一律复制到 `scripts/<chain>/` 并参数化（API key 与标的地址移入工作目录 config.json，铁律 5），禁止只留桌面项目目录路径——项目目录会被清理，skill 会断链。标的专属的分析/报告脚本可留项目目录存档，但 pipeline 文档引用它们时须注明"专属存档，非复用件"。
