# 判例库（casebook）——判定环节的失败模式库

> **按判定环节组织，不按币组织**——按币存放的教训，下一个币的分析永远不会读到（IQ/LPT/PENGUIN/PYTHIA 四案托管误判同族复发的结构性根因）。

## 这是什么、不是什么（铁律 1 边界）

- 判例＝**方法级失败模式**：某类判定曾经怎么错、靠什么检验区分。允许带案例出处（与 address-book/惯犯库现行惯例一致）。
- 判例**不是结论先验**：它告诉你"查什么、怎么区分"，不告诉你"这个币也是这样"。禁止把任何判例当成对当前标的的预设答案。

## 六字段结构（每条判例固定）

1. **ID+成熟度**：稳定编号（册前缀-序号，只增不改义）；成熟度三档＝单案候选 / 机制成立（机制有数学或协议级解释，单案即可转正）/ 跨案复现（≥2 案）——同 retrospective candidate 纪律。
2. **触发现象**：什么指纹/场景出现时本条生效（这是检索键，写具体）。
3. **禁止推断**：见到触发现象时，哪个"顺理成章"的结论是不许直接下的。
4. **必做区分检验**：把两种解释分开的具体动作（查什么、比什么）。
5. **证据不足时**：检验做不了时允许的最强表述或停止动作（防"一律存疑"和"默认并入"两个方向的偷懒）。
6. **权威与出处**：正确判法的权威规则位置（一行指针，不复述）+ 翻案出处（案名+日期）。

## 使用纪律（写进 workflow 对应步骤，此处是总表）

| 分析环节 | 必读册 |
|---|---|
| 阶段 3 实体表冻结前（跑 entity_identity_gate 之前） | cex-custody.md + entity-clustering.md 全册过一遍触发现象 |
| 阶段 0 分母定夺 / 阶段 2 对账与重放收尾 | supply-accounting.md |
| 阶段 4 对抗复核组装怀疑者 prompt | 三册全部（判例=现成的备择解释清单） |

## 收录纪律

- 入库门槛：翻案经用户终裁，或复盘经 candidate 流程确认。新判例默认同时登记为 evals 候选题（见 retrospective.md 分流决策树）。
- 单册上限 25KB 或 25 条，超限先合并同族模式，不拆新册。
- 与 playbook/pipeline 重叠：判例只写指纹与区分检验，正确判法一行指向权威位置，不双写。
