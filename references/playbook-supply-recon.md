# 分析方法学 Playbook · 供给与对账（分册 1/4）

> analysis-playbook 主题分册之一，覆盖 §1/§1b/§2/§8/§8b；三问框架总纲与分册路由见 `analysis-playbook.md`（索引）。规则行尾标注来源会话。

## 1. 供给基线核定（一切百分比的分母）

**三套口径必须分开拿、分开标注、分开使用，禁止混用：**
- **链上实查口径**：totalSupply/getTokenSupply 直查，精确到最小单位；扣减烧毁地址后得链上可流通基数。
- **第三方流通口径**：CoinGecko/CMC 的 circulating supply（含其对锁仓的人工认定），只作对外可比口径引用，标明"XX 口径"。
- **名义已解锁口径**：tokenomist/DropsTab 类解锁表的"累计已释放额度"——这是**额度**不是**流通**，已解锁未必已进入市场。

**口径混淆是五次分析中最高频的结论级错误源**，四种实翻车形态（来源：五会话共见（IO/OPN/FIL/SIREN/HYPE），2026-07）：
- 把解锁表的"名义已解锁"当成"当前实际流通"，两数可差近一倍（OPN，07）
- 现货持仓快照不含质押部分，直接用会得出大户"几乎全员清仓"的假象（HYPE，07）
- 浏览器榜单存在"过滤后 account 榜"与"全量富豪榜"两种口径，前者漏掉 miner/multisig/合约类大户（FIL，07）
- 链上实查总供应与 CMC 流通量是两套数，报告里必须分开注明来源（IO，07）

**执行规则：**
- 引用任何第三方指标前，先核对该字段的原始标签和定义，再决定它对应三套口径中的哪一套（OPN，07）
- 一切"占流通 %"的结论必须写明分母口径；基于快照的指标必须声明含不含质押/锁仓（HYPE，07）
- 被用户质疑数字时，用可复算的拆数回应（各分项相加还原总数），不直接改口；同时主动复查相邻数字，有出入即修正（OPN，07）。**升级（正式）：拆数必须回原始数据现算，禁止转抄报告口径自证——报告是被审对象，不是证据**。报告内部"多处一致"毫无证明力：错误若源于同一次漏改，图/正文/表格是同源复制、三处一致地错（实锤：SIREN 复述求证环节，用户"49.3 不含四仓"的理解本来正确，分析者引用报告修正表将其"纠正"为错误方向，20 分钟后被用户 65.9−49.3−1.44=15.16 的加法推翻——rug 净出实为 64.5pp，报告与"纠正"双双认账）。配套：**用户复述求证是高信号输入**——复述与报告的每一处冲突按"读者错/报告错"双向可疑处理，逐处回数据裁决，不允许默认报告对（SIREN 交付后追查，07-20）
- **★权限双轨核验（Ownable 弃权 ≠ 无增发权，AccessControl 是第三方安全面的口径盲区）**：GMGN/GoPlus 的 renounced=true 只读 Ownable 的 owner()——对 AccessControl 合约不查角色。凡合约源码含 AccessControl：DEFAULT_ADMIN/MINTER 等角色逐个 `hasRole` eth_call 亲验（selector `0x91d14854`），角色授予史用 RoleGranted 事件 topic0（keccak of `RoleGranted(bytes32,address,address)`）从**部署块**起全史拉取；且"角色在手"与"能否增发"分开验证——实测 creator 仍持 ADMIN+MINTER 但 mint 计数器 immutable 打满、增发链上不可能，两层各自查完才可写"增发已锁死/未锁死"（供给分母的未来变化必须由这两层共同决定）（PING，07-17）
- **【候选·单案】vesting 工厂枚举法（自建解锁表，精度比第三方源高一个量级）**：项目用 VestingFactory/TempHoldingFactory 类工厂批量部署锁仓时，拉工厂合约的创建事件全史（Etherscan V2 getLogs 1000 条/页即可）→ 一次拿全全部子合约地址+受益人+声明额度+期限（SQD 案 257 个 vesting 合约一次枚举）；工厂地址从官方合约仓库 README/文档取。配套口径纪律：**事件里的额度是"声明额度"（expected），实际注入以链上转账为准**——两口径分开列，缺口本身就是发现（声明了没打款/超额注入都值得追）（SQD，07-20）
- **CMC/CG 供给数据可能是冻结快照（老通胀币必查）**：两家同值且精确对应链上某历史时点值 = 数据商快照冻结未更新（LPT 案冻结于 5 个月前的某轮次时点值，低报 11%；归因法=把第三方数字与链上历史 totalSupply 序列对表找到精确命中的时点）。持续通胀/通缩币的供给必须链上实查为准，第三方口径只作对外可比引用且**注明抓取时点**（LPT，07-21）
- **质押型代币必须用"权益 = ERC20 余额 + bonded 质押"合并口径**：bond 时代币 Transfer 进协议金库、ERC20 账本上质押大户全变成"转给协议"——不穿透质押账本，集中度/留存/大户榜全体失真（与本节 HYPE 快照口径坑同族，此处是全账本级）。金库（Minter 类）行替换为残差（金库余额 − Σ已归属 bonded）防双计；操作细节见 data-pipeline-evm §10（LPT，07-21）
- **记账式通胀奖励的"已铸未领"桶单列**：奖励 mint 进金库但用户 claim 才落账的协议，"已铸未领"（LPT 案 11.6% 总供给）既不是协议自有、也不是可动用流通——供给分解必须单列这个桶，混入任何一侧都会错报流通结构（LPT，07-21）
- **"销毁"两形态必须区分口径**：①合约级 burn（转入 0x0 或 burn()，**totalSupply 实减**）②dead 地址沉没（转入 0x…dead 等黑洞，**totalSupply 不减**、余额永久沉死）。正文与供给基线表措辞分开写——后者写"dead 沉没余额"不写"销毁/burn"，"总量−销毁"类算式只对形态①成立，形态②的调整后供应应表述为"剔除 dead 沉没后供应"（外部异构复核抓出混称，EGL1 案 360.5 万枚属形态②）（EGL1 redo2 @CX 复核，07-28）

## 2. 对账关卡（硬性 gate，不过不进分析）

**总原则：重建/采集结果必须与独立数据源精确对表后才允许进入分析。对不上 = 数据有洞 = 回去补数据，不是调整阈值或口头解释。** 各链 gate 形态并列如下，做哪条链就执行哪套：

**EVM（全量事件重建路线）三重校验：**
- 全网余额和 = 0（mint 计负、burn 计正后逐笔累加）（SIREN，07）
- 重建余额 vs GMGN top10 逐个对比，要求 **10/10 精确到个位**；实测数据到 97% 时对账 4/10 MISMATCH、补扫完成后 10/10 全过——证明该 gate 能兜住数据缺口（OPN，07）
- 多链部署的代币做跨链总量对账（A 链余量 + B 链流通 ≈ 总量），wei 级闭合（OPN，07）
- **差额排查必查 Burn/Mint 独立事件**：老合约（2017 版 OpenZeppelin）`burn()` 只发 Burn 事件不发 Transfer——"重放净供给 > 链上 totalSupply"的幽灵差额先查这条再怀疑漏段；操作见 data-pipeline-evm §5（LPT，07-21）
- **校准锚点范式**：重放对象的事件若自带事后绝对值字段（如 Bond 事件带 bonded 总额），逐事件比对作内置校准锚点——状态机漂移即刻暴露，不必等末态对账才发现（LPT，07-21）
- 加分项：重建出的实体控盘占比若与第三方分析师独立披露的同口径数字偏差 <1 个百分点，即构成互证，是结论可信度的最强背书（SIREN，07）

**Filecoin（浏览器 API 准全量路线）：**
- 总量恒等式自检：totalSupply = vested + mined + reserveDisbursed（FIL，07）
- 榜单抓完立即做唯一性断言（assert 无重复地址）+ 跨页自洽校验（如 pageSize=100 第 2 页首条 == pageSize=50 第 4 页首条），别等分析阶段才发现分页参数失效（FIL，07）
- 流水加总出的净流量用"链上余额变化"独立复核；高频地址流水有截断时，以余额差校正净流并如实标注（FIL，07）

**Hyperliquid（官方 API + 快照路线）：**
- 同一指标用两个独立来源对表（第三方面板逐日数据 vs 链上快照差分），**偏差 <1%（实测 0.7%）才可按最高证据级措辞呈现**，否则措辞降级（HYPE，07）

**Solana（免费 RPC 无历史回放时的轻量形态）：**
- 至少做：双口径核定（§1）+ 机械解锁金额整除自证——月转出额能被"配额总额 ÷ 归属月数"整除，即反推还原出 vesting 合约参数，数据自洽性由此自证（IO，07）
- 无系统性对账 gate 本身要写进报告局限（历史部分依赖第三方口径）（IO，07）

**时机纪律：** gate 以数据补扫完成（remaining=0）后的那一轮为准；数据未齐时预跑对账只作提前预警口径问题用，不作放行依据（OPN，07）。

**★缺口期上限论证的口径陷阱——时点净库存差 ≠ 累计流出（正式，量纲错误机制明确）：** 数据缺口段（未采集时间窗）想论证"缺口期藏不下达标实体"时，**禁止**拿"缺口起点库存 − 缺口终点库存"当"缺口期总流出上限"——那是**时点净差**，期间可以有任意多轮"流出又流回"（换手），累计流出可远超净差。TROLL 案实证："缺口期 curve 库存仅净降 8.54%，藏不下 ≥5% 实体"整段被复核推翻——缺口期内单轮做量脉冲瞬时动用即达 16.7-22.3%，当日回吐后净差不显示。**缺口期的实体排查正解＝回补数据**（定向拉缺口段逐笔/余额点，TROLL 案用 curve ATA 1,633 笔成功交易的 postTokenBalances 直读回补出 owner 级峰值表），或如实写"缺口期实体活动不可排除"，不许用净差杜撰上限（TROLL 分析复核，07-29）。

## 8. 创世/空投 cohort 留存 + 质押修正

- cohort 定义：创世分配/空投名单（有官方全量表的直接用，如 genesis 余额表；没有的用首批 claim/分发接收地址重建）（HYPE，07）
- 留存率 = 当前持有（含质押）/ 初始分配，分档统计（如 ≥90% / ≥50% / ≥10% / 清零）
- **快照口径必须声明含不含质押**：现货快照不含质押中的部分时，把币质押了的大户会被误判为清仓——曾出现修正前后"保留≥50% 的大户数量"相差近一个数量级、结论从"几乎全员清仓"整体反转的案例。凡链有原生质押/锁仓，留存与集中度指标一律先做质押修正（逐地址查质押余额合并）再计算（HYPE，07）
- **top-N 快照做留存有幸存者偏差**：掉出榜外 ≠ 卖出（可能只是被质押挪出现货榜或被稀释）；留存分析要用全量快照或逐地址点查，不能只看榜单变化（HYPE，07）
- **【候选·单案】质押/worker 押金桶的内部人构成分解（"协议锁仓"表面中性、实际可能高度内部化）**：把质押押金合约的存入方逐个分层——①官方自营地址直押（硬边）②官方 vesting 合约直押 ③vesting 受益人地址直押 ④真外部 EOA——前三层都是内部人押金，只有④是外部参与。SQD 案 2.395 亿押金中真外部仅 3,940 万，"协议质押"桶按表面口径会被读成社区参与度的证据。呈现用区间：内部化程度给"硬边下界（仅①②）~ 含受益人上界（①②③）"两档，避免受益人归属争议把结论打死（SQD，07-20）

**质押/锁仓型标的：Transfer 数据看不到"是否已解押"——必须 eth_call 直读状态（硬性，2026-07-25）**：
全量 Transfer 只能看到"币在质押合约里"，**看不到它处于 staked 还是 unstaked-pending**。
KOGE 案实测：合约实持 1,067,296.56 枚但 `totalStakes()` 只有 168,649.22——**84% 已发起解押**；
最大受益人的 `getStake()`=0、`userInfos()` 待提取额=888,888（占总供应 26.30%），
它存入后 **21 秒**就发起 unstake，`withdrawDelay` 7 天早已届满、此后 14 个月没动。
**结论从"长期锁仓、未离场"变成"随时可提的悬顶盘"——风险画像完全不同，差点交付错误核心结论。**
标准动作三步（凡标的有质押/锁仓合约，除 Transfer 穿透受益人外必做）：
1. `totalStakes()`/合约 `balanceOf` 的**差额＝已解押待提量**（差额大＝锁仓叙事失效）
2. 每个庄级受益人的 `getStake()` / `userInfos()`（后者常含待提取额与时间戳字段）
3. `withdrawDelay()`/`unstakeDelay()` **及其 setter 的 owner**——owner 能改延迟＝**能单方面冻结这部分供给**，
   是反向对手风险，必须与"持有人随时可提"并列写进报告
ABI 从 Sourcify v2 `?fields=abi` 取，selector 用 pycryptodome `Crypto.Hash.keccak` 现算。

## 1b. 多链标的：先判"能不能相加"，再谈分母（GMX 三链案 2026-07-26 定，补多链关卡的量化判据）

SKILL.md 的多链硬关卡要求"各链 RPC 实查该链供给"，但**没说清实查完之后能否相加**。GMX 案给出了判据：**镜像型跨链桥下，各链 `totalSupply` 相加是重复计数**。

**恒等式验证法（一次 RPC 就能定性）**
```
锁仓型主链的桥适配器持币量  ≈  Σ(其余各链 totalSupply)
```
成立 ⇒ 其余链是主链锁仓的镜像，**全局真实总供应 = 主链 totalSupply**，不可相加。
GMX 实测：Arbitrum 锁仓适配器持 **733,655.04**，Avalanche **635,046.17** + Solana **98,409.61** = **733,455.78**，差 199.26 枚（**0.03%**）＝跨链消息在途量（官方桥限速 10,000 枚/4h，在途余量在此量级内合理）。若按相加口径，全部持仓占比会被系统性低估 **5.8%**。

**三种桥形态与对应处理**
| 形态 | 识别特征 | 供应处理 |
|---|---|---|
| 锁仓型（lockbox） | 主链适配器**持币**，转出时锁、转入时放，主链 totalSupply 不变 | 主链 totalSupply 即全局供应；适配器持仓单列"桥锁仓"阵营 |
| 铸销型（mint/burn） | 适配器**持有该链 minter 权限**、自身余额为 0，转出销毁/转入铸造 | 该链供应是镜像，不计入全局 |
| 原生 OFT | 目标链是全新代币、mint authority 为跨链程序派生地址 | 同上 |

**必做的反例检验（否则恒等式吻合可能只是巧合）**：分支链的历史往往早于当前这套桥（GMX 的 Avalanche 侧 2022-01 就有供应，而 LayerZero 桥 2025-07 才部署，早期走第三方桥）。检验方法＝**按月（必要时创世期按日）重建"分支链累计净供应 vs 主链侧新旧各桥余额合计"，全时段不得出现欠额抵押（负值）**；出现负值即说明有一部分分支链供应从未被抵押、必须计入全局。GMX 案复核用 62 个月逐月＋创世季度逐日重建，无一期为负。

**★混合形态：同一标的可能"部分链是映射、部分链是独立供应"，必须逐链分别判、不可一刀切**（IQ(ETH) 2026-07-26 补）。GMX 案的结论是"全是映射所以都不能加"，但这不是唯一形态——**老项目常见"早年在另一条链原生发行过、后来另起炉灶"，那份旧供应既无桥抵押也不受主链控制，必须计入全局分母**。IQ 实测：4 条 EVM 分支链（Fraxtal/Base/Polygon/BSC）逐链对表全部落在锁仓映射恒等式内（如 Fraxtal 侧 6.4577 亿 ↔ 主链桥锁 6.4581 亿、Base 侧 1.5751 亿 ↔ LayerZero 适配器锁 1.5751 亿**精确相等**）→ 不加；而 EOS 侧 36.63 亿是 2018 年原生发行的**独立第二份供应**，官方文档明写"不运营任何桥"、跨链页面已下线、该链合约多年未更新 → **必须加**。全局真实总供应＝主链 230.39 亿 ＋ EOS 36.63 亿 ＝ 267.02 亿，与第三方站点报数残差 0.00074%（**第三方站点的 total 往往正是这个跨链合计，它与主链 totalSupply 对不上时，差额通常就是某条被忽略的独立供应链，别当成数据错误**）。**判定顺序**：先对每条分支链跑上面的恒等式，吻合的归映射、不吻合的再查有无桥——**无桥且量级对不上 ⇒ 独立供应**。漏掉这一步在本案会把分母算错 13.7%，且所有占比结论同比例失真。

**分母还有第三套口径：自由流通（free float）**（IQ(ETH) 2026-07-26 定）。当存在**大额但从未进入市场的沉淀仓**（未流通的增发在途库存、桥锁仓、长期锁定金库）时，"占总供应%"会系统性掩盖真实的市场结构——**账面口径与自由流通口径可能给出方向相反的答案，两个都必须给**。IQ 实测：一次巨额增发后，账面口径下散户＋质押者从 43.32% 摊薄到 14.89%（**降到 1/3**），而剔除未流通沉淀仓后的自由流通口径同期为 46.00%→47.10%（**几乎不变**）——前者是"账面稀释已发生"，后者是"市场稀释尚未发生"，只给任一个都是误导。**报告纪律**：凡单一实体沉淀仓 ≥20% 总供应，问 3 必须双口径并列，并在 TL;DR 点明"这批筹码是悬顶存量（overhang）而非已实现抛压"。

**报告纪律**：TL;DR 首行的分析范围声明要写清"覆盖链合计占全局 X%"，并说明镜像关系——否则读者会拿它与行情站口径对不上。行情站数字若与链上差异大，用本地供应时间线反查它对应哪个历史时点（GMX 实测行情站的 10,449,597 枚对应 **2024-09-02T07:20:10** 的链上状态、差 999 枚＝0.0096%，可定位到小时级）。

## 8b. 嵌套质押的穿透法（GMX 范式：份额代币余额恒为 0，且份额 ≠ 纯币）

多层 RewardTracker 结构（GMX 式：主池 → Bonus 层 → Fee 层）下，**用户持有的份额代币会被逐层存入下一层，因此其现货余额恒为 0**——直接看份额代币余额会得出"只有一个持有者"的荒谬结论（GMX 实测 sGMX 全部 711.85 万枚都在 Bonus 层名下）。

**两步穿透**
1. **算份额**：对份额代币的 Transfer 流水逐地址累计 `mint(from=0x0) − burn(to=0x0)`，即为该地址当前份额（内部逐层搬运不影响此式）。GMX 实测与链上 `totalSupply` 差 0.002 枚，得 95,944 个持有者。
2. **拆纯币**：份额里混着 escrow 版代币（esGMX 之类），**必须**用 Multicall3 批量查 tracker 的 `depositBalances(user, 标的代币)`（GMX 的 selector `0xf5d9d63e`，两个 address 参数各左填充 32 字节）读出**纯标的币存款**。脚本：`scripts/evm/pierce_stake.py`。

**★份额代理纯币会系统性高估，且各实体倍数差异巨大**（GMX 实测"纯币 ÷ 份额"比值）：
| 实体 | 比值 | 含义 |
|---|---|---|
| 小庄集群 | **1.0000** | 只押本金、一枚 escrow 奖励都不复投（机构式风控指纹） |
| 其他大户 | 0.9755 | 少量复投 |
| 项目方 | **0.0039** | 份额几乎全是 escrow 币而非本币（差 250 倍） |
| 全体质押者 | 中位 0.992 / **均值 0.742** | 散户普遍复投 |

⇒ **历史序列的处理**：`depositBalances` 无法从事件日志重建，只能用份额代理。做法＝**对每个阵营算其当前实测比值，历史序列的质押部分按该比值折算**，使当前时点精确、历史为"该阵营 escrow 复投结构不变"假设下的近似，并把该假设写进局限性。GMX 实测按此修正后，其他大户从 15.70% 降到 15.36%、散户从 45.32% 升到 45.65%。
**顺带的分析价值**：比值本身是行为指纹——比值恒为 1 意味着"不要锁定期衍生奖励、只要本金敞口"，是机构而非散户的取向。

**筛选口径的自查**：按份额排序筛 topN 再穿透时，须验证"纯币/份额"比值的**上界 ≤ 1**（GMX 实测无任何地址超过 1），否则排序会漏掉"escrow 少而本币多"的地址。另须给未穿透的尾部算持仓上界（GMX 尾部 94,444 址中最大单个仅 356 枚＝0.003%，即便全属一个实体也仅 3.07%，不达门槛）。
