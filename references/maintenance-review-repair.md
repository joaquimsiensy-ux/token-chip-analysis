# 仓库维护方法论 — 六视角 review 清单与修复工单模板（维护件）

> **⚠ 分析会话不读本文件。** 本件只服务"给本仓库做 review / 修 bug / 整编瘦身"的**维护会话**，不进任何代币分析上下文。
>
> **这是什么**：2026-08-04 前后三轮全库 review 实战（6.11.0 → 6.13.0 → 6.14.0，合计百余项发现）复盘出的方法论，经用户拍板固化。此前它只散落在 CHANGELOG 叙事里，靠人记；本件是它的唯一权威落点。6.15.0 起历轮 review/修复实际按此执行并持续补层（见文末"实战进化"）。
>
> **核心论点一句话**：几万行代码，任何单轮 review 在数学上都不可能"扫全"——review 是**探测器**，不是证明器。三轮实战证明：**视角决定发现率**，每换一个视角就捞出一层新问题。所以视角不能靠 review 方每轮自选（不可控），要固化成清单每轮全跑。

---

## 一、六视角 review 清单

给 review 方（codex 或任何执行者）的指令**不再是"你再 review 一下"**，而是"以下六条逐条过，每条给出你检查了哪些文件"。六条每一条都有本仓库的真实漏检做出处——不是理论清单，是事故清单。

| # | 视角 | 要问的问题（大白话） | 出处事故 |
|---|---|---|---|
| ① | **字段来源审计** | 每个关键字段的值，是从原始数据算出来的，还是调用者/上游**自己报的**？自报的一律不信，要能离线重验 | 6.13.0 P0-02：采集"声明读了两段"、实际第二段文件不存在，账照样平——账平不等于账全；6.11.0：receipt（完工回执文件）裸布尔自报通过 |
| ② | **失败分支审计** | 每个出错分支，是**拒绝退出**（fail-closed，出错就停）还是打个 warning 继续**装成功**（fail-open）？ | 6.13.0：replay 缺文件只打 warning 仍 gate_pass=true；6.32.0 又扫出 6 处假成功（缺表还打"可安全发布"exit 0） |
| ③ | **新格式的存量迁移** | 上了新 schema/新闸，**旧数据怎么办？新产物谁来生成？**两问答不上来，闸只在测试里成立 | 6.13.0 R1/R2 返工：升 schema 只改了校验侧，真实工作流造不出合规 receipt，已买入活案（QUQ）下次增量采集直接卡死 |
| ④ | **修复点的同族调用面** | 这个修复点在全库还有哪些**兄弟入口**（同样逻辑的另一份实现/另一个调用口）？`rg`（全库文本搜索）列全，一起看 | 6.13.0 复审定性：上一轮三组修复只覆盖主函数、漏同族入口，正是本轮 3 项 P1 的来源；6.9.2：升 schema 版本漏了下游消费者，新产物被裁决链路整体拒收 |
| ⑤ | **双向一致性** | 文档 / schema / 命令行参数 / 测试，同一个事实的 N 份副本**互相对得上吗**？两个方向都要查（文档说的代码有吗；代码干的文档写了吗） | 6.14.0：17 处口径漂移（阈值、支持范围、限速数字在文档与代码各说各话），全是人肉同步副本各自漂的产物 |
| ⑥ | **每道闸的可绕性** | 这道闸是**必经之路**吗？能不能不传某个参数、换个入口、给个空壳就绕过去？ | 6.11.0 B-03：报告编译闸挂在**可选参数**上，不传就没闸——装了等于没装；6.13.0 P0-01：封口验的是文件 A、渲染吃的是文件 B，闸在但路不经过它 |

**对修复 commit 的特别要求**：审"修复"时不只验旧反例关没关，**修复中新建/改写的代码本身要按新功能标准把六条过一遍**（尤其①②两条）。出处：三轮里 5 个新引入的洞**全部**长在修复新建的代码里——修 bug 的代码是重灾区，不是安全区。

**预期管理**："全库 review 通过"≠"证明没有其他问题"（review 方自己也承认这措辞说过头）。正确的预期是：每轮清单全跑后，看**新发现的严重度是否逐轮降级**——这是唯一诚实的收敛指标。

### 可直接复制的标准 review 指令模板

```text
对 <目标范围> 做 review。不接受"整体看了一遍"式交差，按以下六条逐条执行，
每条列出你实际检查了哪些文件（含跳过的理由）：
①字段来源审计：关键字段的值来自原始数据还是调用者自报？自报即缺陷。
②失败分支审计：每个出错分支是 fail-closed 还是 warning 后装成功？后者即缺陷。
③存量迁移：本轮引入的新格式/新闸，旧数据怎么迁、新产物谁生成？答不上即缺陷。
④同族调用面：每个修改点 rg 全库列同族入口，逐个确认是否同步修了。
⑤双向一致性：文档/schema/CLI/测试对同一事实的表述互相核对，两个方向都查。
⑥闸可绕性：每道门禁给出"它是必经之路"的证明，或给出绕过路径。
每项发现必须标注归因（见下），并给出可复现的最小反例或具体文件:行号。
```

## 二、review 报告必填栏：归因

每项发现**强制标注归因**，三选一（这一栏曾靠用户事后追问才补，现为必填）。以下名称与定义是唯一事实源；旧报告里的“新引入/半修残留/历史漏检”分别是前三项的简称：

- **老问题修复不全（半修残留）**——旧 finding 对应的不变量仍能从原入口或同族正式入口击穿。即使新代码参与形成缺陷，只要旧不变量没有闭合，仍归本类（→ 同族清单或修复深度失守，修“工单纪律”）。
- **修复中新引入（新引入）**——旧绕过已经关闭，但 repair diff 新造成生产者/消费者断契约、不可运行、新错误接受面或新失败产物（→ 修复代码的六视角自审失守，修“修复流程”）。
- **历史漏检**——缺陷在本轮修复基线前已经存在，同时既不属于此前 finding 的不变量/同族面，也不是 repair diff 造成的发布可达性（→ 既有 review 视角没照到，考虑补清单）。

**替代解释从严规则（强制）：**

1. 先查旧 finding 的 invariant 与同族正式入口；只要无法排除“旧不变量仍在原入口/同族入口被击穿”，按“老问题修复不全”，不得用“这段 return/字段是新写的”降格成历史漏检或改称纯新问题。
2. 若旧绕过已经实证关闭，而无法排除“repair diff 新造成断契约、不可执行或新接受面”，按“修复中新引入”。
3. 只有证据证明缺陷早于修复基线，且能同时排除前两类，才可判“历史漏检”；“以前没人点名”本身不是历史漏检证据。
4. 报告必须写出至少一个最强替代解释及不采纳理由；证据不足时选前两类中风险更高、会触发重审的一类，不准用“待定/可能历史”逃避止损计数。

为什么必填：只有这一栏能告诉你**该修流程的哪一段**。没有归因的 review 报告只能救火，救不了火源。

## 三、修复工单模板

**病根诊断**：残留的病根是"按反例修"——review 说"receipt 没绑定文件"，补丁就"加个文件哈希"。但这道闸存在的目的（**不变量**，即这道闸要永远保证成立的那句话）其实是："receipt 必须证明四件事——正确的币、完整的区间、正确的文件、且是本次运行产生的"。只修反例＝四个漏水口只堵被指出来的那一个。药方是**按不变量修**。

每个 bug 动手前，工单五栏填全（缺一栏不开工）：

```text
【修复工单】bug：<一句话>
1. 不变量：它违反的规则是什么？（一句话写出这道闸/这段逻辑要永远保证的事）
2. 同族清单：这条不变量在库里还有哪些实施点？（rg 命令 + 结果清单，全列出来一起修）
3. 三件套测试：
   a. 原反例——先写能复现 bug 的测试，确认它红，修完变绿（先红后绿）
   b. 同族变体——同一不变量的其他违反方式至少一条
   c. 失败分支——修复代码自身出错时必须 fail-closed 的用例
4. 新建代码自审：本次新建/重写的文件，按六视角①②两条过一遍的结论
5. 归因预判：这个 bug 属于 新引入/半修残留/历史漏检 的哪类，对应流程段是否要动
```

第 2 栏就是本仓库教训"第八层"（修复必带同族 rg 清单）——它以前是复盘文字，文字教训会衰减（本仓库用五次同族翻案证明过）；写进工单当必经步骤才算闭环。

**批次纪律**：

- **修复批次冻结**：一轮修复期间不掺新功能。基线（被审的 commit）中途动一次，review 方就要重冻结一次，审查对象不稳、验收质量必然打折（6.13.0 期间 HEAD 动了两次的实教训）。
- **最终快照单独验收**：分步修完后，对合并后的最终状态整体过一遍验收，不拿"每步各自过了"凑数。

## 四、防屎山：刹住"出错就加闸"的正反馈

屎山的生成机制不是没有门禁，而是**每出一个错就加一道闸，而每道闸又是新代码、新攻击面、下一轮 review 的新问题来源**。症状指纹：同一概念多套登记（两套 registry、两种命名）、口径漂移批量出现。**闸的数量不是安全性的度量——必经之路上的闸才算数。**

三个方向（按工程量从小到大）：

1. **单一事实源**：同一个概念（阈值、schema、流程边界、版本号）只允许一份机器可读的权威表，代码从它取值、文档由守卫对它**双向**校验（只防"被删"不防"各自漂"的单向 lint 不够）。〔已落地：runtime_docs_manifest（6.23.0）、canonical 契约注册表（6.29.0/6.30.0 合一为 138 条单源）、contract_ids_snapshot 双向快照（6.31.0）〕
2. **减法周期提频**：加法几乎每天一版、减法一月一次是失衡节奏；改为**每两轮修复后强制一轮合并整编**——重叠的闸合并、失效的闸删掉、双份事实源收敛成一份。〔落地记录：6.16.0 与 6.21.0–6.25.0 六步瘦身、6.30.0/6.31.0 收口〕
3. **收敛必经之路**：长期方向——把闸内置到少数几条硬管道里，让"绕过闸"物理上无路可走（"闸必须是必经之路"的终极形态是"路只有一条"）。工程量最大，列为大整编目标，不零敲碎打。

## 五、收口标准：连轴 review 什么时候停

无限连轴的边际收益在跌，而**每轮修复本身自带引入风险**（实测：三轮 5 个新引入洞），修过头反而净增风险。止损线：

- 某轮六条清单全跑后，**P0 为零、新发现全是边角料** → 连轴收口；
- 转入周期制：**每次大改后一轮 + 每月一轮**清单全跑的地毯扫；
- 收口不是终审："通过"只意味着这套视角下没照出东西，新事故补新视角（见归因"历史漏检"分支）。

## 六、实战进化（本方法论提出后补的层，均有原案）

- **同族要关到同一深度**（6.15.0 round4b/4c）：④的同族清单不只"列了没有"，还要"修得一样深"——EVM 侧绑定到原始输入哈希、Solana 侧只绑到中间产物，就是等着被穿的浅口。
- **验收攻击站到对方反例边界外一步**（6.15.0）：验收方不能只复跑 review 给的反例，要在其边界外再造一个变体攻一次。
- **破坏性注入反证**（6.30.0）：验收守卫本身时，逐条注入它声称能拦的坏东西，看是不是真拦——守卫的测试不是"好例子过"，是"坏例子死"。
- **grep 清零不信自报**（6.32.0）：宣称"漂移已清除/残留已删净"的验收动作是全库 grep 到 0 命中，不是看修复方的清单打勾。
- **升 schema 必 rg 全库连下游一起升**（6.9.2 断链案）：③与④的交集专项——版本串是最好的同族搜索词。

## 七、修复闭环的施工与验收节拍

本节只补前文没有固化的闭环纪律；六视角、先红后绿和同族等深仍以一至六节为准，不重复改写。

### 7.1 分层收口与止损

- **新引入、半修残留不分严重度，都要修复后重审。** 为什么：它们说明本轮施工方法仍会造洞，P3 也可能是下一轮旁路的入口。
- **历史 P2/P3 记账后做限定复核。** 为什么：旧边角问题不能无限重置整轮盲审，但也不能从台账消失。
- **连续三次消化仍引入新代码问题就冻结。** 为什么：第三循环以后继续补丁的净风险通常高于收益，应把候选和未闭合点上报裁决。

### 7.2 批内审查节拍

固定顺序是：施工 → 独立复核并由裁判代 commit → 批内对抗审查 → 消化 → 增量重审 → 裁决。为什么：执行者不替自己宣布通过，审查对象也始终对应一个冻结候选。

每次消化只改审查点名项；重审先复测旧 finding，再审修复代码自身。为什么：先确认旧洞闭合，才能区分“半修残留”和“修复新引入”。

### 7.3 diff → finding 映射

每个 hunk 必须同时有 invariant、finding/豁免、目的和测试 owner，候选的未映射 hunk 必须等于 0。为什么：没有 owner 的改动无法证明属于哪条修复承诺。

以下三条是映射表通例原文，回填时逐字执行：

> 区间末端恒取候选 tip；自指式 SHA 回填 commit 计入本区间。map 行文件清单以 Fable 实际 commit 分组为准；一文件含多 owner 的 hunk 时（文件级 commit 无法拆分），物理归属行与语义 owner 行互相注明，Fable 回填 SHA 时校正清单。

为什么：commit 是物理容器，invariant 是语义归属；两者不总能一一对应，必须互注而不能硬凑。

### 7.4 攻击式验收的角色分工

- **施工者造红例并修绿，独立审查者站到边界外一步再造变体，裁判冻结口径。** 为什么：同一人只复跑自己的反例，最容易漏掉同族浅修。
- **声明与磁盘实态分别验。** 为什么：manifest 说“不在场”不等于文件真的不在，receipt 说 PASS 也不等于 data 可重算。
- **正例先删旧产物，再由真实 producer 重新生成。** 为什么：这能防止测试把仓库自带 fixture 或上次残留冒充本轮执行证据。
- **同族入口关到同一深度。** 为什么：只给主入口做哈希、别名或错链反例，兄弟入口仍是等价旁路。
- **注入须自证到达目标分支。** 破坏性注入若被路径防护等前置闸拦下，看似“守住”实为未测到目标；注入脚本必须先证明真的走到被测分支再谈结论。

### 7.5 transport-only fake 与 fixture

端到端正例只允许替换 transport；每条注入必须登记五字段：生产 callsite、协议、fake backend/loopback server、测试 ID、允许理由。为什么：少任一字段，就无法判断 fake 是否偷偷绕过了 producer、runner、receipt builder 或 consumer。

手写 PASS receipt 只可用于单元 schema/validator fixture，不得冒充端到端执行成功；旧 schema fixture 必须显式走 legacy-read-only 或负例路径。为什么：fixture 能证明“校验器如何解释字节”，不能证明生产流程真的运行过。
