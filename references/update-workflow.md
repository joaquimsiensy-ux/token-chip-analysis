# 增量更新工作流（/token-update 专用）

> 用途：对本 skill 产出过的研报做**增量刷新**——只拉上次数据截止点之后的链上数据，回答"有没有新庄冒出来、旧庄在增持/减持/清仓、观察哨触发了没有"，交付**轻量更新简报**（不是重做全量报告）。v2.1.0 新增（2026-07-14 用户定，形态 A：轻量增量简报）。
>
> **省什么、不省什么**：省=全量转账重拉（几小时）、实体表从零重建、背景调研全量重做；不省=对账关卡、判级标准的严格执行、对抗复核（缩放版）、呈现纪律。**增量省的是采集，不是判断**。

## 铁律：一切以当前 skill 版本为准（用户 2026-07-14 指定）

旧研报可能产于旧版框架（五问版/旧阈值/行内置信度 tag/旧命名）。更新时**判定标准与呈现规范一律按当前版本执行**：

1. **判级阈值与标签体系**：全部实体（旧的+新的）按当前 analysis-playbook §6a 重新判级——重判成本极低（对着阈值表算一遍），没有理由沿用旧级。
2. **命名/措辞/报告规范**：钱包标签制、【总量X%】、证据强度用词、JSON schema 全按当前 report-template.md。
3. **框架命题**：简报的直答结构用当前版本框架（见 U5 骨架），不跟随旧报告的命题结构。
4. **标准迁移标注**：实体判级/称呼与旧报告不一致时，必须区分两种原因并显式标注——持仓变动所致（正常写）vs 标准变更所致（标注"标准迁移：旧版判 X，按现行标准为 Y，非持仓变动"）。不标注会让读者把标准变化误读成庄家行为。
5. **版本判定**：开工读当前 CHANGELOG 首版本号；旧 appendix.json 的 `token.skill_version`（v2.1.0 起新报告必填）缺失时视为未知旧版——不用猜，反正全部重判。

## U0 定位旧研报与资产盘点

1. **定位目录**：用户给了路径直接用；只给代币名则在用户工作目录（及其上级）搜 `<代币>*分析*`、`*<代币>*` 目录；多候选用 AskUserQuestion 让用户选，零候选如实报告并建议 /token-analyze。
2. **资产盘点**（决定能不能做增量、能做到什么程度）：

| 资产 | 位置 | 缺失时兜底 |
|---|---|---|
| appendix.json（买入过的）或 analysis-state.json（v3.3 起默认交付的机器子集，键名同构） | 旧研报目录 | 两者都无且是 v3.2 前旧报告：从 HTML 的 `id="report-extract"` 块抽取四键，详细键从报告正文/附录 B 补。**外包会话产物旧研报**可能用自定义附录 id（实例 `chip-appendix`）——grep `<script.*json` 找块；其 monitoring_advice 若是裸地址数组，喂 verify_balances 前须适配成 `[{"watch": addr}]` 格式（来源：GME(Robinhood) 增量更新，2026-07-15） |
| 期末余额快照（replay_final_balances / effective_balances 之类） | data/ | **硬前提**。缺失→改为链上实查当前余额重建榜单（Multicall/RPC 批量，仍远比重拉转账便宜）；实查也不可行→**降级建议 /token-analyze 全量重做，不硬凑**。**格式必查**：旧版快照可能是 float"枚"而非 wei 字符串（float64 精度不足 wei 级，直接喂 replay_inc 错 10^18 倍）——旧全量转账在场时用 `scripts/update/rebuild_wei_balances.py` 从零重放出 wei 快照（88 万条约 10 秒），顺带独立复验旧账本（供给闭合+逐址互验）（来源：CASHCAT(Robinhood) 增量更新，2026-07-15） |
| 原始全量转账（*.jsonl.gz / *.csv） | data/ | 非硬前提。缺失→新庄溯源无法回查历史，简报局限性里声明"新实体的早期建仓行为不可考"。**CSV 格式旧全量**（外包产物常见）：喂 scripts/update/ 前转成 jsonl.gz 行格式 {block, ts, tx, logi, from, to, amount(str wei), txfrom: null, txto: null}——txfrom 置 null 不影响重放/对账，只是失去旧段代发者穿透维度（来源：GME(Robinhood) 增量更新，2026-07-15） |
| gas 溯源数据（gas_in.jsonl 之类） | data/ | 非硬前提，但**必查覆盖期**：此类文件只覆盖旧数据期，增量窗口新大户的"共同 gas 金主"维度天然是盲区——U1 就决定：要么补拉增量窗口 gas（gas_trace_bs.py），要么简报局限性显式声明该维度未检验（来源：RAXOL 增量更新怀疑者复核 2026-07-14） |
| 旧报告.md / findings.md | 目录 | 旧结论清单来源；缺失从 HTML 正文读 |

3. **旧实体表继承前的 getCode 复检（硬步骤，不可省）**：旧 whale_groups 里全部"漏斗/中转/马甲"角色地址逐个 `eth_getCode` 体检+疑似者查浏览器 counters（总 tx/币种数）——EVM 用 `scripts/update/getcode_recheck.py`（v2.10 收编，appendix 全地址一键复检+EIP7702 识别）——旧报告的复核修正可能只改了账本/文案而**漏改实体地址表**（TRASH 案：旧会话复核已识别出 UniversalRouter 透传并修正账本，但 0x53bf 仍留在庄#1 的 19 址表里被增量更新继承，实体定义错误随 appendix 传代）。复核修正的教训：**一处结论有多处落点（账本/实体表/图/JSON/文案），修正必须全落点同步**；增量更新作为下游，对继承资产负复检责任（来源：TRASH(Robinhood) 增量更新，2026-07-14；RAXOL 同类教训见 data-pipeline-robinhood.md 方法论坑）。
4. **增量起点**：**一律从旧原始数据末行取**（EVM=区块号、Solana=slot+签名），`data_cutoff` 时间戳只作人读参考——时间→区块换算有缝隙，数据末行天然无缝。原始转账缺失时才用 data_cutoff 换算（EVM 二分定位块高，并把起点前移一段做重叠去重）。
4b. **缩写地址继承禁令（硬步骤）**：旧研报观察哨 check_hint、正文、findings 里出现的**缩写地址**（`0x5d63…`、"0xf36f swapper"之类），继承进本次任何脚本/名单前必须在旧全量数据文件里 grep 前缀解析成完整地址——**手工按记忆补全=编造**。实锤案例：旧报告"税 swapper 0xf36f"被按缩写手工补成错误完整地址，主分析一度产出"税机制暂停"假发现+一条对着不存在地址的假阴性哨兵，靠交叉验证与两路对抗复核独立抓回（来源：VEX(Robinhood) 增量更新，2026-07-15）。
4c. **旧研报无监控包兜底（v3.2 起未买入标的的默认形态）**：appendix.json 与观察哨本就不存在不是资产缺失——实体表从附录 B＋`data/` 落盘产物重建（whale_groups 成员从报告正文实体章节+附录 B 对照拼装）；U3c 观察哨核查如实写"该报告无观察哨基线（未买入未生成监控包）"；U5 滚动 appendix 免做、改滚动 analysis-state.json（v3.3 起默认交付有它；更早的无监控包旧研报本次更新时顺手建一份）。**用户做更新时表示已买入/准备买入的，简报交付后顺手按 monitoring-package.md「买入后监控包」节补建监控包**（观察哨基线从本次更新数据起算）。v3.3 起新研报默认自带 `analysis-state.json`（appendix 机器子集）——有它则实体表直接读取，免于从附录 B 文字重建；scripts/update/ 的 verify_balances/analyze_inc 已自动兜底读取。**3.19 起 whale_groups 带 entity_id 稳定主键**：实体跨期跟踪（旧庄四态/判级变化）一律按 entity_id 对齐，label 只是展示文案可改措辞；滚动重写 state 时 entity_id 终身不变、新实体分配新 id 不复用；旧 state 无 entity_id 的，本次更新顺手补上（按 label 对应关系一次性分配）。顶层 provenance（schema_version/skill_commit/data_sources）滚动时同步刷新。
5. **计划落盘**：一段话（旧截止点 / 增量窗口天数 / 预估增量数据量 / 走哪条管道）+ 开工版本自查（同 SKILL.md 阶段 0，交付前重读版本号防并行会话竞态）。

## U1 增量采集

> **EVM 通用件（v2.10 收编，六次实战抽象）**：U1–U5 的采集/重放/对表/分析/序列五个环节有现成脚本 `scripts/update/`（pull_inc / replay_inc / verify_balances / analyze_inc / camp_series_inc / getcode_recheck / v3_positions），步骤映射与输入输出约定见该目录 README——先用现成的，别再手写；Solana 不走该目录（见 README 跨链路由）。

- **同一条链、同一套管道**（data-pipeline-<chain>.md + scripts/），只把起始参数换成 U0 增量起点；采集标配纪律不变（限速实测/退避重试/断点续传/冒烟小样先行）。EVM 直接 `scripts/update/pull_inc.py`：起点自动=旧数据末行块（含重叠窗），拉完自动做重叠窗一致性校验（FAIL 即退出，不许带伤进 U2）。**v2 parquet 资产例外**：旧数据是 fetch_hypersync_v2 的 parquet run 目录时不走 pull_inc.py（它面向 v1 CSV）——直接用 fetch_hypersync_v2 新起 run（from_block=上次 done.json 的 next_block，付费档 7 万块 2.3 万条实测 4s），重叠核验改为补拉重叠段落盘 patch 目录、按 (tx,log_index) 键对比零差即接（来源：QUQ(BSC) 完整版增量，2026-07-22）。
- **Solana 且旧研报为锚点法（无全量流水）时**：走快照对比法（data-pipeline-solana §10，snapshot_diff.py + probe_window_moves.py 五步）——不补拉全量转账,大额变动地址 100% 覆盖定性替代重放。
- **重叠窗去重**：从末行区块 N（含）开始拉，比对 N 块内容与旧数据一致后再拼接去重——防 off-by-one 漏块/重块（增量特有坑）。
- **报价币侧定向流水**：旧观察哨含报价币侧条目（稳定币余额基线、USDG/WETH 挂单撤单、创始人资金分发）时，U1 必须同步补拉对应报价币在增量窗口的定向 Transfer（涉哨兵地址双向即可，不用全量）——只拉标的代币会让这类哨兵不可核查（来源：VEX(Robinhood) 增量更新，2026-07-15：哨兵 8 条中 2 条依赖 USDG 侧数据）。
- 价格：只补增量窗口（GeckoTerminal / binance.vision）。
- 社媒轻量脉搏：1 路 agent 快查官推/公告/重大新闻（停更？异常公告？舆情事件？）——问 4 的轻量版，**有异常才**扩展成全量背景调研（research-workflows §1）。

## U2 对账关卡（轻量版，硬性——不过不进分析）

1. **增量重放**：旧期末余额快照 + 增量转账 → 最新全量余额表。EVM 用 `scripts/update/replay_inc.py`（全局 (tx,logi) 去重+供给闭合+每地址窗口统计一次算好；旧全量在场时加 `--full` 双路径互验）。
2. **抽样对表**：名单=全部旧 P0 实体地址 + 最新 top20 + 随机 5 个中小户，重放余额 vs 链上实查精确对表。EVM 用 `scripts/update/verify_balances.py`（名单自动构建=实体表∪观察哨∪top20∪随机5；归档块探测对齐时点，wei 级精确口径）。
3. **供给闭合**：增量窗口 mint−burn 配平，总量恒等式复验（replay_inc 已内置）。
4. 对不上=增量数据有洞（最常见：重叠窗处理错、窗口内漏段）=回 U1 补，不许"差不多"。

## U3 增量分析（方法全部引用当前 analysis-playbook）

> EVM 数据底稿一键出：`scripts/update/analyze_inc.py`——四态表（组级合并）、新庄候选双口径（现仓∪窗口净增，防"旧仓+新吸跨线"漏检）、观察哨 mode-aware 逐条核查、窗口买卖榜（全窗净变化口径，v2.7.0 NOXA 教训已固化）。脚本只出候选与画像，**溯源/聚类/判级仍是人工活**。

- **a) 新庄扫描（核心命题）**：在**最新全量余额榜**上扫，**不是只看增量流水**——地址可能旧仓 3%+新吸 3% 跨线，只扫增量流水会漏。候选=不在旧实体地址集合（appendix addresses ∪ whale_groups.addresses）、且**合并关联地址后**当前 ≥ 小庄线（当前版本阈值）。两类都算：**新面孔**（旧数据期几乎无仓）与**升级实体**（旧报告"其他大户"阵营爬上来的）。候选溯源=首笔进货/gas 同源/关联聚类（playbook §4–§6），回查本地旧全量数据（免费）。**贴线集群的"观察组"披露范式**：窗口内同向大额买家（窗口净买前 N 名）合计逼近或按"若视为一体"口径越过小庄线、但无合并硬证据（零互转+funder 不收敛）时——"无新庄"阴性结论照写，但必须①正面披露该组的合计与同时刻合并峰值（sig 原子化口径）②声明"结论成立依赖'无合并实锤'判断而非数字余量"③全组并入同一观察哨（互转/同源注资/同步卖出任一出现即合并重判）。有效否定证据的主次：互转边为零 + funder 不收敛是硬的；"钱包出生时间分散"是弱辅助（庄家囤旧钱包常见），不得单独作为不合并依据（来源：PUB(Solana) 增量更新对抗复核，2026-07-15：三家 4.97% 的"距线 0.03%"叙事被复核指出——第四家并列即 5.51% 破线，安全边际叙事不成立）。**★观察组独立性检验必须把候选放回全历史回放，不能只查增量窗口**——窗口内三件套（互转/funder 收敛/同窗指纹）全阴性≠独立：实锤马甲边（资金直供+整包归集）、与旧实体建仓期的秒级穿插、程序化拆单指纹可能全部在窗口前的旧数据里，增量的窗口切分本身就是盲区；标准动作=对每个观察组候选 grep 旧全量数据出完整历史（建仓时间/来源/与旧实体成员的时序交织），有旧期活动的一律并入怀疑者复核范围（来源：GME(Robinhood) 增量更新对抗复核，2026-07-15：窗口内全阴性的"独立买家"被全历史回放翻出实锤马甲+与在场庄建仓期 4-26 秒穿插，观察组被拆为独立/高度疑似两档，敏感性双口径入报）。**深挖任何可疑地址前先跑 `scripts/labels/label_lookup.py` 批量查一遍，再对 address-book.md 全文 grep**——公共设施（卖出执行合约/聚合器/入金服务）多数已有档案，直接引用省去逐个画像（VEX 增量案 3 个"待查大户"库里全有，重复深挖两轮；来源：2026-07-15。批量层 v4 2026-07-17 覆盖七链主表 ~17.9 万条+privacy 29 万，新增惯犯 SERIAL 段——增量扫新庄时命中惯犯层=最高优先级信号；Pointless 二次增量首战即命中另案实锤集团 2 址潜伏仓，回报确凿）。**★协同实体检验双面纪律（token 面 + ETH 资金面）与深挖线条款**：全套细则见 playbook §6「gas/资金面溯源纪律」——token 面四维全阴性≠独立，合并铁证可 100% 落在 ETH 资金面（九址工作室实锤案在该条）；≥1% 候选的资金对手方无条件展开。**★"旧期零交织"要查行为交集不只持仓交集**：候选在旧数据期的同块协同/等比买卖前科（当日清仓的波段不留持仓端点）必须扫旧全量的逐块行为——三胞胎马甲旧期 150 条同块等比协同、窗口起点持仓为 0，持仓交集检验完全漏检（来源：同上）。**★份额候选线之外必须补"低档同秒共现扫描"+gas 档案双向反查**——两条 ★ 硬步骤全文与 TRASH 漏检实锤（9 址族钻候选线 3.69%、漏反查金主 1.37%）见 playbook §6「行为指纹判定」与「gas/资金面溯源纪律」，增量新庄扫描逐条照做。
- **b) 旧实体逐个对比**：current_share（重放最新）vs 旧 share → **增持/减持/不变/清仓**四态表；跌破线/清仓的按当前阈值重判（多半转离场庄）。
- **c) 观察哨核查**：旧 monitoring_advice 逐条对照增量数据——sentinel 地址动没动（动了=重大事件，单列分析）、threshold 地址累计减持是否过线。这是简报对用户最有操作价值的一节，一条都不许漏。**★addresses 表的 watch_return 条款（"重新持币=回场信号"类）同属哨兵核查范围**——主哨 monitoring_advice 之外，旧 appendix addresses 里带 watch_return=true 的地址组要合并余额对比一遍，回场触发写进哨核查表（实锤：庄#1 集团 8 址回场买入 1.9 千万枚，属 addresses 级条款事实触发，主哨 9 条全不覆盖，差点漏报）（来源：TRASH(Robinhood) 增量更新，2026-07-17）。**旧版 appendix（v1.x）无 mode 字段时，analyze_inc 的自动核查按 any_out 兜底，会把 threshold 语义的旧哨（"余额跌破 X"类）误报为触发——必须逐条人工按旧哨 trigger 原文语义复判**（CASHCAT 案："跌破 100 万枚"哨被"窗口有转出"误报，实际 380 万未破线）（来源：CASHCAT(Robinhood) 增量更新，2026-07-15）。反向漏报同样存在：**trigger 原文含复合条件（"增持至>3% 或清仓"）时，自动核查只判阈值腿、漏"或清仓"腿**——某哨净卖 0.836% 未过 1% 阈值被自动判未触发，实际已清仓归零（清仓腿字面触发）；mode-aware 结果只作初筛，人工复判必须逐条对照 trigger 原文的每一个"或"分支（来源：Pointless(Robinhood) 二次增量，2026-07-17）。**预测追踪三维评分（v3.0，retrospective「预测追踪」节）**：哨核查完成后顺带产出并写进简报——①事实归因（U4 旧账本抽验：对/错/未验）②行为预测（哨兵：兑现/未兑现/窗口未到）③价格结果（单独记，不得反向证明归因对错）；这是报告质量的外部校准，兑现率在整编时汇总。
- **d) 旧结论修正**：**沿用≠盲信**——旧报告结论被增量数据推翻/削弱的，显式列进"结论修正清单"（如旧判"大庄#1 在场护盘"，增量显示其清仓）。
- **e) 开放条款（轻量）**：更新窗口内的结构性异常（暴跌暴涨归因/池子异动/权限变更/异常对倒）照 SKILL.md 开放条款报告，确无则明写"无"。

## U4 对抗复核（缩放版，不可全免）

- **有新庄候选 / 升级实体 / 旧结论重大反转** → 至少 2 路怀疑者 agent（给数据文件路径让它自己重算，强制构造备择解释）——新庄认定是简报的核心输出，错判成本最高（dust 投毒、服务地址误聚类都在历史上发生过）。
- **无新发现** → 本地反例自查至少做两项：①阈值边缘名单（当前 4–5% 总供应档的实体）逐个过一眼防漏检；②观察哨核查的窗口完整性复验（增量数据是否覆盖了整个窗口）。**"无新庄"是阴性结论，同样要经得起反驳**。
- **阴性结论的证明强度声明范式（简报必写三件套）**：①依据类型——"关联证据全阴性"（列扫过的边类型：互转/一对多分发/代发指纹/等额指纹/同窗建仓/gas 同源）还是"数量不足"，两者强度不同；②数学上界——窗口新建仓合计占比若超小庄线，必须明写"数学上无法排除全同源军团的极端假设"；③跨链盲区量化——经桥/托管通道入金的新建仓合计 X%、上游不可穿透，结论限定"链上可分辨口径"。禁止把"关联证据阴性"写成"逐个溯源均为独立散户"（对抗复核抓出的过度断言实例；来源：VEX(Robinhood) 增量更新，2026-07-15）。
- **怀疑者任务必须含一路"旧报告关键账本抽验"**：给怀疑者旧报告的核心逐笔定性账本（费领取/成本/归因表），让其 RPC 抽验 2-3 笔原始交易——旧基线错误不会出现在增量数据里，只有回头验旧账才能抓到（CLUDE 案：dev"费领取"账本 3/3 抽验被推翻，整个成本口径作废重算；根因是旧脚本缺陷，见 data-pipeline-solana §3a.8）。**抽验对象优先级：支撑旧报告核心数字的逐笔定性账本（费/成本/归因）> 实体表 > 观察哨基线**（复核资源有限时按此序分配）。
- 修正顺序照旧：先修数据管线再修文案。

## U6 复盘沉淀（照 retrospective.md，不可省）

更新任务常无新工具知识——"无新增"也走流程（AskUserQuestion 确认 + 成本指标记 CHANGELOG；更新任务预算参考：轮次 <60、活跃 <40min，超了如实报告原因）。若该代币在项目 memory 有结论存档条目，提醒用户追加一行最新状态指针（指向更新简报文件，不复制结论细节进 memory）。

**成本纪律同样适用（v3.1）**：更新会话照执行 SKILL.md 成本纪律三刀——U1 增量采集/U2 对表等机械环节外包 `model: sonnet` 子代理、上下文超 30 万在阶段边界建议断点、复盘在轻上下文里做。更新任务本该是轻量任务，上下文失控多半意味着违反了"禁止整读旧报告"（U0 只读附录 JSON 与实体表，不整读旧报告正文）。

## 何时不该用增量更新（改走 /token-analyze 全量）

- 旧研报缺期末余额快照，且链上实查重建榜单也不可行（见 U0 资产表）。
- 距上次研报太久（>2 个月）或窗口内主战场变了（合约迁移/换池/跨链扩展）——结构变化大到旧实体表参考价值崩塌。
- 发现新 P0 级实体且其行为贯穿旧数据期——说明旧报告可能整体漏判，该重做全量而不是打补丁。
- 同一研报已连续 3 次增量更新未做全量——债务攒够了，做一次全量重置基线。
