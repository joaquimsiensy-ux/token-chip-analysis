## R7-06 消费面评估

现状机器扫描只有 `solana-window-fetch-receipt/v2` producer，没有正式 consumer。`window_fetch.py` 是发射窗/事件日高密度区间的按需补采工具，并非每个 Solana 正式案都必跑；因此本阶段若把该 receipt 无条件加入 handoff READY 必备槽，会错误阻断没有调用 window fetch 的正常案例。把文件仅塞进通用 data map 也只能绑定字节，不能证明其 schema、target、PASS/0、range 和 output file_ref 语义，属于低成本假绑定。

裁决：本阶段不扩大 handoff/data-map schema。后续最小正确方案是先由 canonical Solana collection plan/job spec 明确声明本 run 是否调用 window fetch；一旦声明调用，受控 runner 必须要求对应 `solana-window-fetch-receipt/v2` 为 formal、target 一致、PASS/0、range 与计划一致且 output file_ref 有效，再把 receipt+output 一起绑定到 handoff/data map。该条件式消费切片需独立反例，不与本轮三项摘牌混改，交 Fable 验收裁决。

## `net.py` 系统性放大点六视角自审

1. **字段来源**：Result 只由 subprocess 完成态、stderr/stdout 和本地 JSON/NDJSON 解码构造；HTTP 类别只认 `curl --fail-with-body` 的 rc=22，其他非零归 transport。
2. **失败分支**：布尔隐式转换、returncode 非零、超时/OSError、空 stdout、单 JSON 失败、NDJSON 任一行失败均有硬失败；仅所有行可解析才返回 value。
3. **存量迁移**：`RpcPool/http_get_many` 未改签名、返回结构或消费者；新 Result 没有混入旧字典接口；anchor 旧行不猜测升级而是重采。
4. **同族调用面**：本轮只将任务书点名的 anchor/window 从裸 curl 迁到 `net.py`；`fetch_hypersync` 等未出 finding 的采集件零触碰；manifest 明确区分共享 curl 后端与两个 net 调用点。
5. **双向一致性**：producer schema 仍为 v2；kernel 自动绑定 target/producer/mode/inputs，独立 receipt validator 与 shared consumer继续重算 producer/output 哈希及 PASS coverage。
6. **证据与消费**：离线故障注入覆盖传输、HTTP、decode、结构化空、resume 身份、cutoff、反向/负窗口、gap stale、receipt 写失败；未发真实链请求，避免把网络可用性混入本地门禁正确性证明。
